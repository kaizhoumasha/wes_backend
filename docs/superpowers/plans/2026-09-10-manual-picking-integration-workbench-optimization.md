## 1. 成功标准与范围

1. 可以从已发布的 MANUAL PickingTask 开始，完成资源计划、搬运、人工拣料、退箱/离场及 WMS 任务完成确认。
2. 同一任务可以同时包含传送带料箱与退料货架直接取料；两条路径各自推进，按合同在任务收尾汇合。
3. 支持多料箱、多批次、多个货架面和计划增量，不能仅演示一个料箱的一次直线流程。
4. 操作员能在发送前调整请求、查看实际 wire 和校验差异，并从已确认事实继续联调。
5. 每次通过都能追溯请求、响应、回调、业务应用及所需物理结果；模拟或人工录入结果不计入真实全流程通过。
6. 同一组场景后续用于自动 handler 验收，分别记录“人工驱动全流程通过”和“插件自动全流程通过”。

本次不实现 PDA、库存裁决、供应商私有协议、通用流程设计器、动态 operation registry、热加载业务代码或全自动 manual-picking handler。旧 manual_bin_processing 插件按既有约定保留。

现场曾在授权下把已有 Run 切到真实模式并沿用原请求身份。这是历史处理事实，不作为自动迁移模拟动作的产品行为；仍按 §3.4 区分历史模拟记录与真实动作，新实现不得重标历史成功或自动补发。

**回调修正操作准则：** 区分“submit 被拒”与“已接纳任务的 result 回调被拒”。本例属于后者：保存原 transport_task_id；同一实际结果的修正沿用 outcome_revision=1，修改报文使用新的 canonical UUIDv7 operation_id，通过正式事件入口提交。原报文同内容重试保留原消息身份；不能复用已拒绝消息身份修改正文。实际结果修订遵循结果合同，不能把本例固定 revision 的做法推广到所有修订。

**最新合同决定（用户已确认，待实施）：** 货架结果回调的 arrival_face 为可选项。缺省、null 或空字符串均表示“未提供实际面向”，不得仅因此返回 REJECTED/INVALID_EVIDENCE；即使原请求提供了 target_face，也不要求补填 arrival_face 才能接收。上述 610007 被拒是旧实现的历史事实，不是后续验收要求。

**成功结果的面向保证（用户已确认）：** WMS/RCS 部分成功回调不返回 arrival_face，但保证按请求的 target_face 到位。因此，对于已关联原请求且其他成功条件成立的货架 SUCCEEDED 结果，arrival_face 缺省/null/空字符串时，若原不可变请求中存在有效 target_face，WES 使用该值确定到位面向，来源标为“依据成功结果与请求推导”；显式回传的非空 arrival_face 来源标为“回调提供”。该保证是合同依据，不是无条件用计划目标猜测位置。

补值只能读取该 TransportTask 实际发送的冻结 target_face，不能读取最新计划、页面草稿、旧位置投影或示例值。原请求也没有 target_face 时面向仍未知；FAILED、UNKNOWN、尚未完成或无法关联原请求的结果不使用该推导规则。显式返回的面向优先按适用合同校验；与原请求不一致时不得覆盖成 target_face 来掩盖冲突。

满足其他完成条件的 SUCCEEDED 结果正常接收、应用并闭合原 Transport；不能在业务应用阶段重新以缺少 arrival_face 为由拒绝同一结果。位置投影使用本次回传或合法推导的面向；两者都没有时保存未知，不沿用旧面向冒充此次确认。后续需要实际面向的动作可使用该合同保证下推导的值；仍未知时按该动作所需事实单独校验，不反向否定本次搬运成功。

提供非空 arrival_face 时仍按不透明字符串原样保存，并执行适用的类型、长度、字符及实际结果一致性校验；不因可选而接受任意错误类型。空字符串按缺失处理，非空文本不 trim；空白字符串是否有效仍服从统一面向合同。该规则限适用的货架结果，不将 arrival_face 扩展为任意结果类型的合法字段。

实施须同步 Transport 履约合同、wire/OpenAPI、结果应用、位置投影、SDK 相关合同及联调前置条件。缺省/null/空字符串的规范化及幂等摘要由共享入口统一处理；target_face 推导在匹配原任务后的共享结果应用层完成，不重写原始报文、接收摘要或消息身份。结果查询和导出应能区分回传值与推导来源，优先引用既有原请求/Evidence，不重复保存完整报文或建立独立来源状态机。

**恢复与展示：** 页面提供原请求、被拒原报文、字段级错误、可复制的修正草稿及可靠身份；自动填充能证实的关联字段，对缺失物理事实保留空值和说明。若增加授权补录操作，显示事实来源及操作者，经正式入口接收后继续检查 Evidence 应用、原 Transport 终态和对应步骤重算。旧告警保留历史，当前告警只在其实际条件已解除时清除；不能整 Run 清空所有异常。

**资源到位的分支规则：** 五层架到位由所属 Transport 和实际位置/面证据证明；outbound.return_rack.arrival_report@v1 只属于计划中的退料货架。direct_picks=[] 不产生该义务；计划缺失或尚未应用不能当成空集合。混合计划按对应 rack/face 检查已创建的报告及确认，不因 A 分支不存在报告而阻塞 A，也不能因 B 尚未闭合而提前结束整个任务。

**验收分层：** 本次证明了两架的真实下发接纳及补录后的继续条件，不证明供应商原生结果回调已经修复，更不证明 manual-picking 全流程通过。补录解阻与原生回调符合性分别出具结果；供应商修复后仍需真实回调验证。

### 3.1 Run 和步骤实例

- Run 记录实际插件版本、工作线及配置快照、任务关联、操作者和环境；不成为新的 PickingTask 或正式执行身份。
- 同一 Run 下可有多个分支和步骤实例。实例记录场景步骤代码、对象关联、前置证据引用、请求冻结稿、可靠动作引用、结果和触发来源。
- 料箱条码不是本次物理动作的唯一身份；引用原始事件和当前动作关联。直接取料使用 task_id/rack_id/rack_face，不能套用 Bin 字段。
- 保留现有 Run/Step 表，增加必要的分支/对象关联和证据引用；移除单一 current_phase 作为全流程约束的设计。优先引用已有模型，不另建完整业务对象副本。
- FIFO 与面级完成属于插件业务记录；仅保存后续动作真正需要的记录，通过正式 Repository/Service 维护，不以联调日志冒充已应用业务事实。
- 刷新或重启后，从持久化步骤与已有可靠对象恢复页面。关闭 Run 仅结束联调记录，不取消外部任务、释放物理围栏或抹去未闭合义务。
- 人工与自动路径不得为同一源事实各创建一个动作；复用既有业务动作身份与事务校验，触发来源只作记录，不作为新幂等身份。

### 3.2 上下文带入与编辑

自动填入工作线资源、计划 revision、WMS 返回目标、实际扫码和原 operation/command/transport identity，并展示每个值的来源。操作者可以修改未发送草稿；不可覆盖已接收事实或已冻结请求。

| 内容 | 编辑规则 |
| --- | --- |
| 当前合同允许的业务参数 | 草稿可编辑，提交前校验与当前对象/前置事实一致 |
| 工作线、实际设备/位置 | 从已配置资源选择；绑定变化不能悄悄覆盖正在执行的快照 |
| operation_id、command_code、已冻结正文 | 创建后只读；技术重试复用原内容和身份 |
| 真实事件及完成事实 | 选择和引用，不能编辑；手工备注不改变其来源或应用状态 |
| 响应/回调中新字段、错误枚举及结构 | 原样有界观察并展示合同差异；不能自动接受或映射为成功 |

### 3.3 资源货架搬运及已交付优化的承接

完整位置组合以[货架搬运规则](../../integration/manual-outbound-rack-transport.md)为准，联调流程采用以下已确认映射，不另建可任意组合的模板配置中心：

| 计划角色 | 出库 | 换面 | 回库 |
| --- | --- | --- | --- |
| target_rack，转运货架 | F01 | CK04 | F01 |
| bin_source_racks，五层货架 | CTU01 | CTU02 | CTU03 |

- 角色来自已应用 plan_delta，不按货架号前缀、位置编码或未知角色兜底猜测。direct_picks 引用的退料货架另按其批准合同处理。
- 第 4 步只逐架创建出库 MOVE_RACK，不同时预建换面/回库动作。出库 wire 使用 RACK(货架号) → RACK_POSITION；无需操作员补填来源精确库位，但不取消公共 Transport 对本次动作实际适用的事实校验。
- 前端展示逐资源列表及原 TransportTask 状态；后端同时校验角色、模板、目标位置和计划面。面向为不透明字符串，"90"、"270" 原样传递。
- 转运架目标来自实际 TRANSFER_RACK 绑定；五层架目标来自 FIVE_RACK 所绑定的实际资源及其容量语义。当前热补丁的 OUT65、KT16/KT17 只是旧现场配置，不能固化为新插件拓扑，也不能把 FIVE_RACK 的排队容量解释为多个独立位置编码。
- 计划资源超过 FIVE_RACK 可用容量时，后续货架等待容量，不要求操作员给每架选择不同目标位置；目标始终解析为同一个已绑定工作位。
- 换面目标必须是有证据的当前实际位置，回库目标取自 WMS 权威决定；不从计划目标推断当前位置。

#### 单工作位、按容量呼叫五层货架（用户已确认）

FIVE_RACK 只有一个工作位，配置容量 C 表示整个五层货架区可容纳 C 架，包含 1 个作业位及 C−1 个排队位。容量配置复用 WorkLine 唯一入口；不增加“逐架/预呼叫”模式开关，C=1 自然逐架处理，C>1 允许提前呼叫后续货架。

- **Wire 决定：暂不通知 WMS 修订。** `added_bin_source_racks[]` 继续一项表示一个来源货架面，`rack_face` 保持单值字符串；不增加 `rack_faces` 数组或双格式兼容。货架和面别的组织由 WES 完成。
- WMS 来源成员仍以 `task_id + rack_id + rack_face` 识别并保留原 revision/Evidence；WES 在当前任务内按 rack_id 聚合待处理面，呼叫、排队和容量按物理货架计算，批次请求、面级完成和换面按货架面处理。聚合不改写原始 wire，也不合并不同任务的业务终态。
- bin_source_racks 不是同时可作业的工位列表。WES 按批准的本地调度规则冻结货架及面处理顺序；公共合同未赋予数组顺序业务含义前，不把数组首项当作 WMS 指定优先级或首次目标面。具体选序规则在任务 1 闭合；已有队列不能因页面刷新而重排。
- 同架另一面追加到后续 revision 时，更新该架待处理面，不因新成员自动再建入站搬运。已在途、排队或作业的货架复用本次物理关联；若该架已离区，则按新的有效需求和容量重新准入，不能永久按 rack_id 禁止后续呼叫。
- 页面按货架展示当前面、待处理面、已完成面和运输状态。每面的 `RACK_FACE_DONE` 独立处理；`NO_BATCH` 不表示该面结束或授权换面。换面及货架退出条件继续遵循所属合同，不因聚合自行增加业务规则。
- 可继续呼叫数量为 C 减去已占用容量及已呼叫尚未到达的预留容量。每架只计一次；创建可靠搬运时原子预留，到达时转为占用，避免并发点击或在途请求造成超呼叫。复用已有资源准入及运输身份，不另建一套锁或运输队列。
- 所有五层货架呼叫都使用同一绑定位置和 CTU01；后台按剩余容量与顺序校验，前端默认选中可呼叫的连续前缀。第 4 步不再把第一个/第二个来源架映射到 KT16/KT17。
- 呼叫可以提前，但业务作业逐架进行。到达该货架区不等于已进入作业位；排队进位及实际作业架必须有所属 ECS/RCS 合同的权威事实，不能仅凭计划顺序或运输 ACK 推断。具体排队和进位机制作为任务 1 的现场合同闭合项，不虚构额外排队位置编码。
- 容量只有在匹配的离开该区域事实、或明确未执行且已解除预留的权威终态后释放。超时/未知不能自动释放；同架原地换面、仅业务完成或发出回库请求也不释放容量。队列范围是本线 FIVE_RACK 区，不影响独立的转运架/退料架分支。
- 一个货架离开作业位进入区域内其他位置，不等于离开区域；后续已排队货架按实际进位事实开始作业。已呼叫但结果未知的原动作不换身份重发，不越过未闭合队头。
- 联调阶段人工点击“呼叫下一架/按剩余容量呼叫”，每架独立创建可靠 TransportTask 并展示部分提交结果；重试只补未创建且仍可准入的成员。handler 完成后复用同一规则自动触发，不能并行建立第二套调度逻辑。

以本次计划为例，假设 WES 已冻结 510002/"90" 先于 510012/"270" 的处理顺序（不是由 wire 数组自动授予优先级）；610007 使用独立 TRANSFER_RACK，不占 FIVE_RACK 容量。C=1 时先呼叫 510002，待其按合同离开区域并释放容量后再呼叫 510012；C=2 且区域空闲时可依次呼叫两架，510012 排队，取得实际进位事实后才开始作业。C 大于计划资源数时只呼叫实际存在的资源。

页面显示“容量 C、作业架、排队架、在途预留、待呼叫资源和可用数量”；这些是已有事实的展示，不额外创建独立状态机。若共享位置准入当前只支持单占用，实施前将容量消费者列入影响清单，不绕过位置冲突检查来实现排队。

### 3.4 模拟与真实下发的可见性

- 创建 Run 时明确展示 WMS、Transport、ECS 各自的实际连接/执行方式。沿用现有 profile，不把 CONTRACT_SIMULATION 文案理解为所有外部系统都必然模拟。
- Transport 的 CONTRACT_SIMULATION、DEVICE_INTEGRATION 结果显示“模拟搬运，未创建真实 TransportTask”；FULL_SITE_INTEGRATION 才具备真实搬运路径。执行按钮标明“模拟”或“创建真实搬运”，不能仅显示“成功”。
- 真实搬运分别展示“TransportTask 已创建、已向 WMS 发送、WMS 已接纳、权威结果已接收/应用”。按部署实际运输链显示 WES→WMS→RCS，不将 WES 提交笼统写成直接向 RCS 下发。
- 通过已有 Transport/诊断记录关联实际任务身份、发送尝试和响应；无 transport_task_id 的模拟记录不能计作真实任务或参与真实通过判定。
- Run 已产生动作后，不直接改 profile 将历史模拟步骤转为真实步骤；新建真实 Run 并重新校验可复用的权威前置事实。原模拟步骤保留来源，不能自动重放生成实机动作。
- 若需结束原模拟 Run，先检查它是否已形成真实 WMS 义务或其他外部副作用；不能以“模拟”名义自动关闭未决义务。

## 4. Wire 快速试验边界

提供表单与 JSON 双向编辑、最终发送预览、请求/响应对比和样例导出；不要只展示“预期请求”，必须可核对实际发出的请求及实际接收内容。复用 WMS 诊断记录和设备 ingress history，对未进入 Evidence 的拒绝也展示原因。

### 4.1 正式全流程路径

已批准 typed operation 仍走原严格 DTO、WmsConfirmation、DeviceCommand 或 TransportTask。参数、样例及已有配置变化可以现场重测；业务身份变化需新步骤并满足原动作的状态约束，不允许“改 JSON 后换 ID 重发”处理未知物理结果。

### 4.2 Wire 探测

保留一个明确标识的独立探测入口，用于验证待协商的 data 字段、类型及枚举，避免生产 DTO 在发送前消灭待观察差异。其首轮范围是固定、已批准的 operation 目标和配置的联调端点；不开放任意 URL、Method、operation 字符串或任意协议脚本。

- 复用现有有界单次 HTTP 收发与诊断；探测记录不进入正式 Confirmation/业务应用，不建立第二套重试队列。
- 每次发送保存准确正文和身份；不自动重试。外部有副作用的探测仍可能改变 WMS 状态，不因本地称为探测就视为无副作用。
- 首轮活体探测限供应商隔离测试数据/测试端点；目标不满足隔离条件时仅允许离线差异校验。不得在活动业务上下文里以原始报文绕开动作准入。
- ECS 实体动作仍通过 DeviceCommand 的目标/命令准入；任意 wire 变体只在供应商模拟端点验证，不提供绕过可靠执行的实机命令通道。
- WMS/ECS 入站仍使用唯一正式入口并按当前合同接收或拒绝；查看原始请求及拒绝理由，不增加“宽松接收后转正式 Evidence”的平行路径。
- 探测成功不自动进入全流程上下文。只有确认并更新正式机器合同后，才能在正式路径重新验证和计入通过。

该入口是联调工具例外，不能作为插件的 generic call，也不对 SDK 导出。任务 1 的工程评审必须明确批准此限定例外；若不批准，保留正式编辑、离线校验和证据对比，并如实标记原始报文发送未交付。

**预期收益：** 参数、合法值、请求样例及隔离 wire 假设无需逐轮发版；新 operation、正式 DTO/语义变化仍需要一次合同落地与发布。不能承诺所有协议变化零代码、零发布。

## 7. 验证矩阵与门禁

| 场景 | 必须观察到 | 不得发生 |
| --- | --- | --- |
| 零 handler | 合法设备事件可靠留证；人工流程可按合同发起 | 自动默认放行或假报插件处理成功 |
| 资源货架出库 | target_rack→F01；bin_source_racks→CTU01，角色、位置、面向与计划一致 | 统一 CTU01、未知角色兜底或目标超容量 |
| FIVE_RACK 容量 1/2 | C=1 逐架；C=2 可预呼叫两架但逐架作业，均指向同一绑定位置 | 将两架映射到两个工作位、排队架提前进入作业 |
| 同架多面及追加 | 同架 90/270 两条成员占一个容量、当前入站只呼叫一次；各面独立取料和完成，追加面关联现有货架 | 按面重复搬运/计容量、误把另一面标完成、修改 WMS wire 为数组 |
| 在途与补位 | 在途计预留；真实离区后可补下一架；并发点击不超额，增量计划不重复 | 超时释放容量、同架换面释放容量、重复刷新重复呼叫 |
| 换面及回库 | 转运架 CK04/F01、五层架 CTU02/CTU03，符合已冻结位置合同 | 仅页面新增枚举、用计划目标冒充实际换面位置 |
| 模拟转真实 | 模拟明确未下发；新真实 Run 创建可追溯任务并显示发送/接纳/结果 | 改 profile 将模拟 SUCCEEDED 变成真实通过或自动补发 |
| arrival_face 可选及成功推导 | 省略/null/空字符串不单独导致拒绝；SUCCEEDED 且原请求有 target_face 时据其推导并标明来源，否则面向未知 | 要求 WMS 补面才继续、失败结果推导、读取最新计划或旧投影、覆盖显式冲突 |
| 回调真正不合法 | 展示具体字段级拒绝原因和原任务状态，修正经正式入口应用 | 把被拒回调当未收到、修改原消息正文重试、重发搬运 |
| 到位分支隔离 | direct_picks=[] 时五层架无需退料到位报告；非空时核对对应成员报告，缺计划则等待 | 对全部货架强制 return_rack.arrival_report 或全局跳过报告 |
| 补录与恢复 | 真实事实确认后正式补录、Evidence 应用、原任务闭合、相关告警重算；保留人工来源 | 直接更新状态、清除无关告警、宣称供应商回调或全流程已通过 |
| A 正常多箱 | 每箱独立事件/动作，FIFO 退箱，真实目标搬运结果 | 一个 bin_code 覆盖整个 Run，越序退箱 |
| A 的 NO_WORK/NG | 各自匹配业务决定，NG 不进入正常回流 | 无完成事实仍按 WORK_REQUIRED 放行 |
| B 独立及多面 | 面级完成匹配，必要换面/退场，原 Transport 结果 | 假扫码、假 Bin、PICK_AND_PUT |
| A+B 与计划追加 | 双分支独立推进，当前修订所有必需成员闭合后完成 | B 等 A 的扫码或忽略追加成员 |
| wire 不一致 | 原请求/响应/拒绝及字段差异可见；隔离探测可调整重测 | 自动宽松接受并推进业务 |
| 重复/断线/超时 | 身份稳定、原对象可恢复、迟到结果可关联 | 换身份重发未知物理动作 |
| 真实通过 | WMS 业务终态与合同要求物理结果均可追溯 | 以模拟响应、手工确认或 HTTP 200/202 替代 |
| 后续自动接入 | 相同场景由 handler 触发且没有重复动作 | 将人工操作绿灯计为自动插件绿灯 |

验证执行：

- FAST：`uv run pytest tests/runtime/workline_integration_debug -q`，并选择实际受影响 WMS/设备合同与诊断测试；执行前检查收集范围。
- 插件：`uv run --extra manual-picking pytest workline_plugins/manual-picking/tests -q`，按插件 pytest 配置显式区分 FAST 与真实集成，不让默认命令误启重测试。
- 前端：定向运行 manual-outbound-integration 的 Vitest；合同变更执行 `pnpm run contract:freeze`、`pnpm run contract:verify`，权限变化执行 `pnpm run permission:verify`；真实页面使用浏览器 QA。
- migration：独占临时 PostgreSQL，在干净逻辑库上验证迁移链及 schema；不使用共享开发数据库。
- HEAVY：扩充精确 mapping。现有联调 mapping 仅指向 schema 测试，不能证明新业务事务/worker；基础 HEAVY 按 selector 执行，插件真实集成单独运行。
- 最终 QUALITY、必要 HEAVY、真实 worker 和迁移各在有效快照执行一次，后续仅刷新失效证据；不把环境缺失导致的 skip 当通过。

效率验收在同一环境记录改造前后结果：合法参数修改到重测结果所需时间、每轮手工复制身份次数、一次断线恢复是否需重走前序、同类 wire 试错所需发布次数。目标是合法参数和隔离样例重测无需发布，实际请求/响应能直接定位差异，而不是预设没有依据的百分比。
