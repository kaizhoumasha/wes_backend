# 权限目录与菜单真源收敛设计

**状态：** APPROVED TARGET

**日期：** 2026-08-20

**范围：** `/Users/kaizhou/codeDev/wes_backend` 与 `/Users/kaizhou/codeDev/wes_frontend`

**发布基础依赖：** `docs/superpowers/specs/2026-08-25-frontend-backend-release-decoupling-design.md`

## 1. 问题

当前系统同时维护五份相互重叠的数据：后端路由权限声明、数据库权限目录、前端路由菜单元数据、数据库菜单树和静态生产初始化 SQL。当前代码扫描得到 145 个权限节点，而静态 SQL 保留 149 个节点；当前前端菜单为 14 项，而静态 SQL 保留 25 项。部署链路实际执行动态同步，静态 SQL 已经退出真实执行路径，但仍被测试和文档引用。

问题不是单次漏同步，而是同一事实存在多个可写真源。继续补齐 SQL、菜单表或数量阈值，只会推迟下一次漂移。

## 2. 决策

### 2.1 权限定义

- 后端 FastAPI 路由上的权限声明是 API 权限定义的唯一真源。
- `wes_sys.permissions` 是代码定义的物化目录，只供查询、角色授权和 API Application 授权使用。
- 权限目录不得由管理页面或运行时业务 API 创建、修改、移动、软删除、恢复或永久删除。
- 权限同步必须精确收敛：创建缺失项、更新元数据漂移、物理删除代码中不存在的项，并由外键级联清理失效关联。
- 扫描结果为空、重复权限码对应不同路由、权限码格式非法或事务中任一步骤失败时，拒绝写入并整体回滚。

### 2.2 角色与初始化

- 用户、角色以及用户-角色、角色-权限关系继续由数据库持久化。
- 五个内置角色定义集中在一个后端基础服务中；开发 seed、生产 bootstrap 和权限同步脚本复用它。
- 生产 fresh DB 由一个 `bootstrap_foundation` 入口创建/修正内置角色、同步权限目录、精确收敛内置角色权限、创建首个超级管理员并确保其关联“系统管理员”角色。
- 后续部署使用同一权限目录服务执行显式 `--apply`，随后以 `--check` 验证零漂移。

### 2.3 菜单

- 前端静态路由及其 `meta.menu` 是菜单标题、路径、图标、排序和层级的唯一真源。
- 前端从唯一 `createRoutes()` 路由装配和统一 `RouteMeta` 类型合同读取静态元数据，使用当前用户权限集合过滤并构造菜单树；无可见子项的分组不显示。
- 后端删除菜单表、角色菜单关系、菜单 CRUD、菜单同步、菜单缓存和 `/auth/my.menus`。
- 前端删除菜单 API、菜单管理页面、菜单 manifest 发布产物以及后端菜单缓存/回退路径；登录、刷新、重试、token refresh 和 logout/login 均不得发起菜单网络请求。
- 系统不存在独立的“拥有 API 权限但仍隐藏菜单”策略；若未来出现明确需求，必须另行建模，不恢复 `role_menus`。

## 3. 边界

### 3.1 基础能力

- 认证、权限扫描、权限目录同步、角色授权、首个管理员 bootstrap。
- 使用最小 FastAPI 测试应用和独立 PostgreSQL 测试库验证，不依赖 WorkLine、Transport、WMS、ECS 或设备业务场景。

### 3.2 业务能力

- 各业务路由只声明自身需要的权限码。
- 业务测试验证业务接口的授权接入，但不能替代权限基础能力测试。

### 3.3 表现层

- 菜单只是前端导航投影，不是后端安全边界。
- 后端权限校验始终是最终裁决；隐藏菜单不能代替 403。

## 4. 合同

- `/api/v1/auth/my` 最终只返回 `user` 和 `permissions`。
- `/api/v1/auth/permissions` 作为同一权限服务的窄刷新接口保留，不构成第二权限真源。
- `/api/v1/admin/permissions` 最终只保留查询能力；OpenAPI 中不得出现其写操作。
- `/api/v1/api_auth/applications/available-permissions/sync` 删除；API Application 页面只读取和分配已经同步的 `app_api` 权限。
- `/api/v1/admin/menus/**` 全部删除。
- `permissions` 表保留；`menus` 和 `role_menus` 表删除。

## 5. 明确非目标

- 不建设策略引擎、权限注册中心、动态菜单平台、配置中心、事件总线或插件体系。
- 不保留旧字段、旧接口、别名、shim、双读、fallback 或空实现。
- 不转换旧菜单数据；开发和测试数据库直接重建。
- 不借本次工作重写完整迁移历史；菜单删除先使用随机 Alembic revision，后续既定 schema baseline 工作再吸收最终模型。
- 不修改、移动或删除 `docs/hardware/`。
- 不以本地 Mock、基础能力测试或浏览器菜单测试证明供应商一致性、现场联调或业务验收。

## 6. 当前落地与发布边界

- 后端权限目录、内置角色、bootstrap 与只读权限管理由当前实现和本设计共同约束。
- 前端菜单投影与后端菜单持久化删除已经收敛到本设计；已完成的实施计划不再作为活动真源。
- 两仓 Commit、镜像和评审证据独立形成，任何一侧的 build、test、publish 都不等待另一侧 Commit、job 或镜像。

菜单删除属于方向不对称的合同变化，发布时按两次独立 FULL 执行：

1. 用 `DEPLOY_SCOPE=FRONTEND` 只输入新前端候选，自动发现并校验当前后端，证明菜单完全由路由投影且浏览器不再请求菜单 API；
2. 用 `DEPLOY_SCOPE=BACKEND` 只输入新后端候选，自动发现并校验已部署前端，再执行不可逆菜单表 migration。

允许“新前端 + 旧后端”和“新前端 + 新后端”；“旧前端 + 新后端”必须由 consumer compatibility gate 在维护前阻断。该顺序来自真实合同方向，不绑定两仓 Commit。

## 7. 完成条件

- fresh DB 通过唯一 bootstrap 入口得到内置角色、精确权限目录和首个管理员。
- bootstrap、权限 `--apply` 和 `--check` 均可重复执行，第二次无变化。
- 数据库权限名称集合与当前后端路由目录完全一致，不使用数量下限判断。
- 权限定义没有人工写入口，API Application 页面没有运行时重新扫描按钮。
- 后端不存在菜单模型、表、关系、API、同步脚本或认证响应字段。
- 前端菜单只由静态路由和当前权限集合产生，权限加载失败时不显示或放行受保护页面。
- 前端阶段和后端阶段分别通过只输入本侧候选的独立 FULL 门禁；当前对端由现场与最近发布证据发现并交叉验证，发布证据不包含前后端 Commit equality。
- 新前端运行时不再请求菜单 API 后，才允许执行后端菜单表/API 删除；旧前端与新后端组合必须在维护前失败。
- 相关 FAST、集成、迁移、QUALITY、HEAVY selector、前端 Vitest、契约门禁和浏览器 QA 均基于最终快照通过。
- 过期过程文档移出项目目录，当前文档不存在旧链路说明，`docs/hardware/` 保持原样。
