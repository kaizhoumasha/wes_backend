# 仓库执行系统（WES）第三方设备统一接口白皮书

## 1. 范围

本文供硬件设备控制系统（ECS）供应商开发人员和仓库执行系统（WES）开发人员使用，规定双方如何通信。设备控制系统供应商需要
实现作业指令和设备状态接口，并按本文要求向仓库执行系统回传任务结果和设备事件；仓库执行系统开发人员需要按同一约定发送
作业指令、查询设备状态并接收回调。

双方固定使用四个接口：

- 设备控制系统提供 `POST /api/v1/device/command`；
- 设备控制系统提供 `GET /api/v1/device/status`；
- 仓库执行系统提供 `POST /api/v1/callback/result`；
- 仓库执行系统提供 `POST /api/v1/callback/event`。

本文只规定双方在网络上传输的请求、响应和字段，也就是网络传输接口（wire），不说明任一方的实现细节。本接口没有取消操作
（Cancel），也不增加供应商私有认证、自动重试或供应商私有路径。

### 1.1 四个接口组成一次完整闭环

一次设备动作不是一个请求就结束，而是分成三个阶段：

1. 仓库执行系统发送作业指令（Command），要求设备控制系统执行一项动作。
2. 设备控制系统返回接收确认（Acknowledgement，ACK），表示它是否已经接纳这条命令。接收确认不是完成证明。
3. 设备控制系统完成动作或确认失败后，主动调用结果回调（Result Callback）。这个回调才报告物理动作的最终结果。

事件回调（Event Callback）用于上报独立发生的设备事件，例如扫码完成或急停按下。仓库执行系统返回的事件接收确认只表示事件
数据已经持久接收，不会在同一个超文本传输协议（HTTP）响应中夹带下一条设备命令。仓库执行系统如需设备继续动作，必须另发
作业指令。

### 1.2 双方职责

- 设备控制系统负责提供作业指令和状态查询接口。调用这两个接口时，设备控制系统是服务端，仓库执行系统是客户端。
- 仓库执行系统负责提供结果回调和事件回调接口。回传结果或事件时，仓库执行系统是服务端，设备控制系统是客户端。
- 双方只通过本文规定的接口交换信息。作业指令和状态查询使用本文规定的字段闭集；结果回调和事件回调只校验必需字段，
  供应商增加的其他顶层字段会被仓库执行系统接受并忽略。双方不得改用私有路径。

### 1.3 术语速查

下表先用日常语言解释术语，再给出技术人员需要遵守的含义。后文出现这些术语时，均按本表理解。

| 术语 | 非技术解释 | 实施时的准确含义 |
| --- | --- | --- |
| 仓库执行系统（WES） | 负责安排并记录现场作业 | 本文中的命令发起方，也是结果回调和事件回调的接收方 |
| 设备控制系统（ECS） | 负责把软件命令交给现场设备执行 | 本文中的作业指令和状态查询服务端，也是结果回调和事件回调客户端 |
| 应用程序接口（API） | 两个系统约定好的通信入口 | 由请求方法、路径、请求数据、响应数据和错误语义共同组成 |
| 网络传输接口（wire） | 真正在网络上传输的内容 | 只包括本文规定的网络请求、响应和结构化数据字段，不包括任一方的实现细节 |
| 服务端、客户端 | 服务端等待请求，客户端主动发起请求 | 作业指令和状态查询由设备控制系统提供；结果回调和事件回调由仓库执行系统提供 |
| 接口地址（endpoint） | 接口的网络地址和固定入口 | `ECS_BASE_URL` 或 `WES_BASE_URL` 加上本文给出的 `/api/...` 路径 |
| 基础地址（Base URL） | 一组接口共同的地址前缀 | 例如协议、主机和端口；具体值由部署配置提供，本文不固定具体地址 |
| 统一资源定位符（URL） | 可以在网络上定位一个接口的完整地址 | 基础地址与固定路径拼接后得到完整接口地址 |
| 超文本传输协议（HTTP） | 系统通过网络发送请求和响应的协议 | 本文使用 `GET` 查询，使用 `POST` 提交命令、结果或事件 |
| 协议状态码（HTTP status code） | 响应中表示请求处理结果的数字 | 例如 `200`、`400`、`409`、`503`；必须与响应 `message` 一起判断 |
| 协议成功状态码（2xx） | `200` 至 `299` 这一组状态码 | 状态查询只把这组状态码当作可继续解析的响应，其他状态都算查询失败 |
| 结构化数据格式（JSON） | 由字段和值组成的文本数据格式 | 本文所有请求和正常响应都按这种结构传输 |
| 对象（`object`） | 由 `{}` 包住的字段集合 | `params`、`data` 和 `error_detail` 都要求是对象，不能用数组或字符串替代 |
| 数组（`array`） | 有顺序的一组值，使用 `[]` 表示 | 状态查询的 `devices` 和错误响应的 `issues` 都是数组 |
| 字符串、整数、布尔值（`string`、`integer`、`boolean`） | 文本、没有小数部分的数字、真假值 | 分别写成字符串、整数，以及 `true` 或 `false` |
| `null` | 明确表示当前没有值 | 只有字段表允许时才能发送；它和字段省略不是一回事 |
| 包络、顶层字段、二级字段 | 包络是整份结构化数据；顶层是最外层字段；二级字段位于对象之中 | 设备业务参数只能放进 `params` 或 `data`，不得提到最外层 |
| 闭集 | 只允许列出的字段，不能自行增加 | 作业指令请求、状态查询和 `error_detail` 按字段表校验；作业指令 ACK、结果回调和事件回调的额外顶层字段会被忽略，事件联调开关 `is_debug` 除外 |
| 载荷（payload） | 一次请求实际携带的数据 | 判断重报、冲突和幂等时，按对应接口章节说明的字段进行比较 |
| 内容类型请求头（`Content-Type`） | 告诉接收方正文采用什么格式 | 本文要求发送结构化数据时使用 `application/json` |
| 统一字符编码（UTF-8） | 中文、英文和符号的统一文字编码 | 结构化数据正文必须能按该编码正确解码 |
| 256 千二进制字节（`256 KiB`） | 单条消息允许的最大体积 | `KiB` 是 1024 字节；`256 KiB` 等于 262144 字节 |
| 一致性验收 | 检查供应商实现是否完全遵守本文 | 至少核对路径、字段、类型、错误语义、幂等、回调和实际设备行为 |
| 作业指令（Command） | 仓库执行系统发给设备控制系统的设备动作要求 | 使用 `command_code` 标识，动作类型放在 `task_type`，参数放在 `params` |
| 设备状态（Status） | 设备控制系统当前报告的设备能力和运行状态 | 仓库执行系统用它判断设备是否在线、自动、空闲且没有活动命令 |
| 接收确认（ACK） | 接收方对请求的确认回复 | 作业指令确认只表示设备控制系统接纳；回调确认只表示仓库执行系统持久接收；两者都不等于物理完成 |
| 持久接收 | 仓库执行系统已经把回调保存下来 | 只证明回调数据已被接收和保存，不证明设备动作成功或下一步作业已经开始 |
| 回调（Callback） | 接收方稍后反向调用原请求方 | 设备控制系统通过结果回调报告最终结果，通过事件回调报告设备事件 |
| 同步、异步 | 同步是当前请求立即返回；异步是后续另发消息 | 作业指令的接收确认是同步响应，结果回调是完成后的异步请求 |
| 物理终态 | 设备动作最终成功或失败的事实 | 只能由匹配 `command_code` 的结果回调报告 |
| 幂等、幂等身份 | 同一件事重复发送时，系统仍只处理一次 | 作业指令和结果回调以 `command_code` 识别；事件核心字段和 `data` 相同时只处理一次 |
| 重报、重提、自动重放 | 再次发送同一份消息 | 只有本文明确允许时才可使用原身份和完全相同的载荷再次发送 |
| 重试等待响应头（`Retry-After`） | 告诉调用方应该等待多久再请求 | 只有 `429 CAPACITY_EXCEEDED` 同时返回有效值时，仓库执行系统才能延后重提 |
| 冲突 | 同一个幂等身份对应了不同合同内容 | 返回 `IDEMPOTENCY_CONFLICT` 后必须停止自动发送并人工核对 |
| 交付结果未知、对账 | 无法确定对方是否收到时，先查证事实 | 禁止直接换身份重发；需要核对仓库执行系统、设备控制系统和设备记录 |
| 纪元毫秒时间（Unix Epoch milliseconds） | 从 1970-01-01 00:00:00 协调世界时（UTC）起累计的毫秒数 | `timestamp`、`finish_time` 和 `updated_at` 都发送整数，不发送日期字符串 |
| 查询参数（Query parameter） | 跟在接口地址 `?` 后面的查询条件 | 状态查询只允许可选的 `device_code`，用于查询单台设备 |
| 枚举 | 只能从预先列出的值中选择 | 例如 `mode` 只能是 `AUTO`、`MANUAL`、`MAINTENANCE` 或 `UNKNOWN` |
| 失败关闭（fail closed） | 信息不可信时选择不动作 | 状态缺失、过期或不合规时，仓库执行系统不发送作业指令 |
| 设备合同附录 | 针对某类设备补充的字段约定 | 只定义 `params` 或 `data` 下的业务字段，不能改变本文顶层网络传输接口 |
| 冻结接口 | 双方已经确认、不能由一方自行改动的接口约定 | 修改方法、路径、字段、类型或语义前，必须重新完成合同评审和一致性确认 |
| 认证 | 接收方确认调用者身份和权限的过程 | 本文不增加供应商私有认证字段或私有认证路径 |
| 诊断字段、`trace_id` | 用于查日志和定位问题的信息 | 不参与业务判断；作业指令响应中的 `trace_id` 可选但不能为 `null`，其他未识别顶层字段会被忽略 |
| 日志 | 系统自动记录的运行过程 | 供应商可用 `trace_id` 在设备控制系统日志中定位一次请求，但日志不能代替结果回调 |
| 在线接口文档（Swagger） | 根据接口定义生成的在线说明页面 | 用于查看和试调接口，不能修改本文规定的请求方法或路径 |

## 2. 公共规则

四个接口共同遵守以下规则：

- 请求和响应通过超文本传输协议传输结构化数据。发送方使用 `Content-Type: application/json`，正文采用统一字符编码（UTF-8）。
- 请求方法和路径以本文为准。在线接口文档只能展示和试调接口，不能覆盖固定路径。
- 作业指令和状态查询的顶层字段是闭集。结果回调和事件回调只校验必需字段，其他顶层字段会被接受并忽略；事件回调可选的
  `is_debug` 是唯一参与处理的公共扩展。设备自己的业务字段
  仍应放入 `params` 或 `data`。
- 双方直接传递 `device_code` 和 `command_code`，不得私自改名为 `device_id` 或 `command_id`。
- 网络传输接口中的时间都使用纪元毫秒整数。不得发送日期字符串或秒级时间。
- 单个结构化数据消息不能超过 `256 KiB`。
- 同步接收确认只证明设备控制系统接纳命令，不证明设备完成动作。物理终态由结果回调报告。
- `params`、结果回调 `data` 和事件回调 `data` 的二级字段由对应设备合同附录定义，不能提升到顶层。
- 核心合同字段只有在字段表明确允许时才能为 `null`。可选对象如果省略，仓库执行系统按空对象处理。任何二级业务字段都不能
  移到顶层。

## 3. 设备控制系统（ECS）接口

### 3.1 接收作业指令（Command）

```text
POST <ECS_BASE_URL>/api/v1/device/command
```

仓库执行系统按下表直接发送结构化数据。最外层只能有这些字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `device_code` | `string` | 是 | 目标设备编码 |
| `command_code` | `string` | 是 | 仓库执行系统生成的全局命令身份 |
| `task_type` | `string` | 是 | 设备动作类型 |
| `priority` | `integer` | 是 | 本轮固定为 `1` |
| `timeout` | `integer` | 是 | 期望完成时间，毫秒 |
| `timestamp` | `integer` | 是 | 纪元毫秒格式的命令创建时间 |
| `params` | `object` | 是 | 业务参数 |

现场第一次联调可以使用下面的格式。示例值用于说明字段位置；实际的设备编码、命令身份、动作类型、时间和参数由联调现场提供。

```json
{
  "device_code": "STATION_SCAN1",
  "command_code": "019f12d0-58d7-7b4d-a23a-1b90aa5d4471",
  "task_type": "MOVE_FORWARD",
  "priority": 1,
  "timeout": 30000,
  "timestamp": 1787440800000,
  "params": {}
}
```

本文只规定 `params` 必须是结构化数据对象（`object`），不规定对象内有哪些业务字段。供应商应按对应设备合同附录实现这些字段，
仓库执行系统开发人员也应按同一附录组装参数。

设备控制系统接纳命令后，应立即返回下面的协议响应和结构化数据。这个响应只确认接纳，不确认设备完成动作。

```http
HTTP/1.1 200 OK
Content-Type: application/json
```

```json
{
  "code": 200,
  "message": "ACK"
}
```

设备控制系统可以额外返回 `trace_id`，帮助供应商在自己的日志中定位这次请求；如果返回该字段，值不能是 `null`。仓库执行系统
只有在以下条件全部满足时，才把响应认定为确定接收确认：协议状态为 `200`，`Content-Type` 为 `application/json`，响应体是
结构化数据对象，`code` 为 `200`，`message` 为 `"ACK"`。未识别的其他顶层字段会被忽略；上述核心条件任一不满足，仓库执行
系统都把本次交付记为结果未知。

设备控制系统必须把 `command_code` 当作命令的唯一身份。同一个 `command_code` 和完全相同的载荷再次到达时，设备控制系统
返回与第一次相同的接纳事实，不能再次驱动设备。若同一个 `command_code` 对应的载荷发生变化，设备控制系统返回冲突。

作业指令响应必须包含 `code`、`message`，并可包含可选且非 `null` 的 `trace_id`；其他顶层字段会被忽略。仓库执行系统必须同时
检查协议状态和 `message`，并按下表处理：

| 协议状态 | `message` | 含义 |
| --- | --- | --- |
| `200` | `ACK` | 已接纳，等待匹配结果回调 |
| `400` | `INVALID_ENVELOPE` | 包络错误，未接纳 |
| `404` | `DEVICE_NOT_FOUND` | 设备不存在，未接纳 |
| `405` | `METHOD_NOT_ALLOWED` | 方法错误，未接纳 |
| `409` | `IDEMPOTENCY_CONFLICT` | 相同身份对应不同载荷，结果未知，禁止自动重放 |
| `413` | `PAYLOAD_TOO_LARGE` | 超过消息上限，未接纳 |
| `422` | `ANNEX_VALIDATION_FAILED` | 设备附录校验失败，未接纳 |
| `429` | `CAPACITY_EXCEEDED` | 未接纳；必须同时返回有效 `Retry-After` 才可按原身份延后重提 |
| `500/502/504` | `TEMPORARILY_UNAVAILABLE` | 交付结果未知，进入对账，禁止自动重放 |
| `503` | `TEMPORARILY_UNAVAILABLE` | 明确未接纳，可按原身份和原载荷延后重提 |

如果响应不是结构化数据、协议状态与 `message` 的组合不在表中，或必填字段缺失，仓库执行系统无法确认设备控制系统
是否接纳，必须进入人工对账。未知额外顶层字段不参与 ACK 判定；`trace_id` 等已知可选字段一旦出现，仍必须满足其类型和值约束。
例如 `{"code":200,"message":"OK","data":null}` 仍进入 `RECONCILING`，原因是 `message != "ACK"`，不是因为存在
`data`。只有两种情况允许重提：请求可以证明没有离开仓库执行系统，或者上表明确写明设备控制系统未接纳。
重提时必须使用原 `command_code` 和完全相同的载荷，不能生成新身份绕过已有事实。

### 3.2 查询设备状态（Status）

```text
GET <ECS_BASE_URL>/api/v1/device/status[?device_code=<DEVICE_CODE>]
```

`device_code` 是唯一允许的可选查询参数。传入它时查询一台设备；不传时查询当前设备控制系统管理的全部设备。成功响应的顶层
只能有 `devices`。`devices` 是数组，每一项必须由 `device` 和 `state` 两个对象组成：

| 对象 | 字段 | 类型 / `null` | 说明 |
| --- | --- | --- | --- |
| `device` | `device_code` | `string`，非 `null` | 设备编码 |
| `device` | `device_name` | `string \| null` | 设备名称，仅诊断展示 |
| `device` | `device_type` | `string \| null` | 设备类型，仅诊断展示 |
| `device` | `role` | `string \| null` | 设备角色，仅诊断展示 |
| `device` | `supported_commands` | `string[] \| null` | 当前设备控制系统声明的命令能力 |
| `device` | `supported_events` | `string[] \| null` | 当前设备控制系统声明的事件能力，仅诊断展示 |
| `state` | `device_code` | `string`，非 `null` | 必须与同项 `device.device_code` 一致 |
| `state` | `mode` | `AUTO \| MANUAL \| MAINTENANCE \| UNKNOWN`，非 `null` | 运行模式 |
| `state` | `status` | `IDLE \| RUNNING \| ERROR \| PAUSED \| STOPPED \| OFFLINE \| UNKNOWN`，非 `null` | 设备状态 |
| `state` | `is_online` | `boolean`，非 `null` | 设备控制系统的在线判断 |
| `state` | `current_command_code` | `string \| null` | 当前活动命令；无活动命令为 `null` |
| `state` | `scenario` | `string \| null` | 设备控制系统联调和诊断场景，不参与作业指令发送判断 |
| `state` | `updated_at` | `integer`，非 `null` | 纪元毫秒格式的状态更新时间 |

`mode` 表示设备由谁控制：`AUTO` 是自动模式，`MANUAL` 是人工模式，`MAINTENANCE` 是维护模式，`UNKNOWN` 表示设备控制系统
无法确认。
`status` 表示设备正在做什么：`IDLE` 是空闲，`RUNNING` 是执行中，`ERROR` 是故障，`PAUSED` 是暂停，`STOPPED` 是停止，
`OFFLINE` 是离线，`UNKNOWN` 表示状态不明。仓库执行系统只能在 `AUTO` 和 `IDLE` 组合下准入，其他值都不能发送作业指令。

下面是查询一台设备时的成功响应：

```json
{
  "devices": [
    {
      "device": {
        "device_code": "STATION_SCAN1",
        "device_name": "扫码工位1",
        "device_type": "SCANNER",
        "role": "SCAN_STATION",
        "supported_commands": ["MOVE_FORWARD", "MOVE_BACKWARD", "MOVE_LEFT", "MOVE_RIGHT"],
        "supported_events": ["SCAN_COMPLETED"]
      },
      "state": {
        "device_code": "STATION_SCAN1",
        "mode": "AUTO",
        "status": "IDLE",
        "is_online": true,
        "current_command_code": null,
        "scenario": "success",
        "updated_at": 1787431993388
      }
    }
  ]
}
```

示例中的 `SCANNER` 是设备类型，`SCAN_STATION` 是设备角色，`MOVE_FORWARD` 等值是该设备声明支持的命令，
`SCAN_COMPLETED` 是它声明支持的事件。`scenario: "success"` 只用于联调诊断，不参与仓库执行系统的准入判断。这些都是示例
字面量；真实取值以设备合同附录和设备控制系统当前状态为准。

带 `device_code` 查询时，设备控制系统必须返回且只返回一个 `device_code` 相同的条目；不带参数时返回全部条目。返回零条或重复
条目、`device.device_code` 与 `state.device_code` 不一致、字段缺失或多出、类型错误、枚举值不在表中，都会使整次状态查询不可信。

仓库执行系统发送作业指令前，需要同时确认五个条件：`is_online=true`、`mode=AUTO`、`status=IDLE`、
`current_command_code=null`，并且 `updated_at` 没有超过双方约定的状态有效期。任一条件不满足，仓库执行系统都不发送作业指令。
`device_name`、`device_type`、`role` 和 `scenario` 只帮助联调人员查看状态，不参与发送判断。设备控制系统查不到设备时返回协议
状态 `404`。
状态查询返回非成功协议状态码时，响应体不属于公共网络传输接口，仓库执行系统只根据协议状态认定查询失败，不依赖供应商私有
错误结构。

## 4. 仓库执行系统（WES）回调接口

### 4.1 回传任务结果（Result Callback）

```text
POST <WES_BASE_URL>/api/v1/callback/result
```

设备控制系统必须使用 `Content-Type: application/json`，并把下表字段直接放在最外层，不能再套一层 `command` 或其他对象。
仓库执行系统严格验证表中的核心字段，同时允许供应商增加顶层诊断扩展字段。

常见扩展名包括 `trace_id`、`event_id` 和 `causation_id`。仓库执行系统接受它们为 `null`，但只把它们视为供应商诊断信息；这些
字段不影响回调是否被接受，也不影响重复回调的判断。`error_detail` 不是自由扩展区，只能包含 `code` 和 `msg`。具体设备结果
放在 `data` 内，其二级字段由设备合同附录定义。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `command_code` | `string` | 是 | 原命令编码 |
| `device_code` | `string` | 是 | 执行设备编码 |
| `result` | `SUCCESS \| FAILED` | 是 | 物理动作终态 |
| `finish_time` | `integer` | 是 | 纪元毫秒格式的完成时间 |
| `data` | `object` | 否 | 设备合同附录定义的业务结果数据 |
| `error_detail` | `object \| null` | 条件 | `FAILED` 必填，`SUCCESS` 省略或为 `null` |

设备动作成功时，可以按下面的结构回传：

```json
{
  "command_code": "019f12d0-58d7-7b4d-a23a-1b90aa5d4471",
  "device_code": "STATION_SCAN1",
  "result": "SUCCESS",
  "finish_time": 1787440804000,
  "data": {
    "actual_qty": 1,
    "move_result": "MOVE_FINISHED",
    "station": 10
  },
  "error_detail": null,
  "trace_id": null,
  "event_id": null,
  "causation_id": null
}
```

成功示例中的 `actual_qty`、`move_result` 和 `station` 都位于 `data` 内，只用于展示设备结果字段应放在哪里。仓库执行系统的
统一网络传输接口不解释这些字段；实际含义和允许值由设备合同附录规定。

设备动作失败时，设备控制系统应按下面的结构回传。如果原有字段名是 `error_code` 和 `error_message`，发送前需要转换成本文规定的
`code` 和 `msg`：

```json
{
  "command_code": "019f12d0-58d7-7b4d-a23a-1b90aa5d4471",
  "device_code": "STATION_SCAN1",
  "result": "FAILED",
  "finish_time": 1787440804000,
  "data": {
    "result": "MOVE_FAILED"
  },
  "error_detail": {
    "code": "TARGET_BLOCKED",
    "msg": "Path blocked"
  }
}
```

联调结果回调时逐项检查：

- 顶层 `result` 只允许 `SUCCESS` 或 `FAILED`；`MOVE_FINISHED`、`MOVE_FAILED` 等设备结果应放在 `data` 内；
- `finish_time` 必须存在且为纪元毫秒整数，不能用 `timestamp` 替代，也不能发送字符串；
- `data` 可以省略并按空对象处理；一旦提供就必须是结构化数据对象，不能为 `null`；
- `SUCCESS` 的 `error_detail` 必须省略或为 `null`；`FAILED` 必须提供仅含 `code`、`msg` 的对象；
- 仓库执行系统返回协议状态 `200` 和消息 `ACK`，才表示结果回调已持久接收。收到协议状态 `400` 时，设备控制系统应读取
  `error_detail.issues[]`，按问题列表修正字段，然后使用正确身份重报。

以下写法会返回 `400 INVALID_ENVELOPE`，因为缺少合法的顶层 `result` 和 `finish_time`：

```json
{
  "command_code": "019f12d0-58d7-7b4d-a23a-1b90aa5d4471",
  "device_code": "STATION_SCAN1",
  "move_result": "MOVE_FINISHED",
  "timestamp": 1787440804000,
  "data": {}
}
```

仓库执行系统使用 `command_code` 识别结果回调。核心字段和 `data` 相同的结果重复上报时，仓库执行系统返回相同的接收确认并且只
处理一次；同一 `command_code` 对应不同合同内容时，仓库执行系统返回冲突。如果仓库执行系统不认识该 `command_code`，则返回
协议状态 `404`。

### 4.2 上报设备事件（Event Callback）

```text
POST <WES_BASE_URL>/api/v1/callback/event
```

设备事件是设备主动发生的事实，不是某条作业指令的完成结果。仓库执行系统验证下表核心字段，同时允许设备控制系统增加顶层
诊断扩展字段。除可选的 `is_debug` 外，这些扩展字段只用于诊断，不影响事件是否被接受，也不影响重复事件的判断。设备自己的
事件数据必须放在 `data` 内，具体二级字段由设备合同附录定义：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `device_code` | `string` | 是 | 上报设备编码 |
| `event_type` | `string` | 是 | 设备合同附录定义的事件类型，例如 `ESTOP_PRESSED`、`MATERIAL_ARRIVED`、`SCAN_COMPLETED` |
| `timestamp` | `integer` | 是 | 纪元毫秒格式的事件时间 |
| `is_debug` | `boolean` | 否 | 现场联调开关；省略等同于 `false`，不接受 `null`、字符串或数字 |
| `data` | `object` | 否 | 设备合同附录定义的业务事件数据 |

```json
{
  "device_code": "STATION_SCAN1",
  "event_type": "SCAN_COMPLETED",
  "timestamp": 1787440805000,
  "data": {
    "barcode": "BIN_104"
  }
}
```

示例中的 `barcode` 是设备附录字段。仓库执行系统在这层只把它当作扫描到的料箱编号（BIN），不把物料的 `6 合 1` 等复合
业务数据塞进这个值。统一网络传输接口不规定 `data` 的二级字段，不同设备可以不同；供应商和仓库执行系统必须以对应设备合同
附录为准，并把这些字段留在 `data` 内，不能提升到顶层。

事件回调没有单独的事件身份字段。核心字段、`is_debug` 和 `data` 相同的事件重复上报时，仓库执行系统返回相同的接收确认并且
只处理一次；省略 `is_debug` 与显式传入 `false` 视为相同事件。

当 `is_debug=true` 时，该事件只用于现场联调，不进入 WorkLine 或业务处理。仓库执行系统持久化事件并独立返回 ACK，异步可靠
命令链路随后尝试下发 `MOVE_FORWARD`：联调期间目标固定为 `http://10.24.209.26:8080/`，EVENT 的 `data` 原样作为
`MOVE_FORWARD.params`。仅当 ECS Status 声明支持 `MOVE_FORWARD` 且设备通过现有在线、AUTO、IDLE、无活动命令等准入检查时才
发送。WES 中同设备已有未终态命令时，新 EVENT 仍被持久化和 ACK，但不会创建或发送新 Command；现场应使用返回的旧 `command_code` 按原身份对账，不得换新命令重发。没有 WES 未终态命令但当前 ECS Status 不满足准入时，已创建的联调命令以失败终结，不等待后续自动补发。重复 EVENT 最多创建一条命令。

仓库执行系统成功接收并保存结果回调或事件回调后，统一返回：

```json
{
  "code": 200,
  "message": "ACK"
}
```

这个接收确认只表示仓库执行系统已经持久接收。响应中不携带作业指令；包括 `is_debug=true` 触发的联调命令在内，任何下一步
设备动作都通过第 3.1 节的作业指令接口另行发送。ACK 响应与命令创建属于独立异步路径，仓库执行系统不能证明设备控制系统在
worker 启动前已经读取该响应。

结果回调和事件回调的错误响应必须包含整数 `code` 和字符串 `message`。`400 INVALID_ENVELOPE` 表示结构化数据包络不符合合同，
此时还必须返回 `error_detail.issues[]`。`issues` 中的每一项说明一个问题：`field` 是字段路径，`code` 是稳定错误码，
`expected` 可选，用于说明期望类型。为避免泄露数据，响应不能回显字段值、原始载荷或未经处理的异常信息。其他错误码不返回
`error_detail`：

| 协议状态 / `code` | `message` | 处理语义 |
| --- | --- | --- |
| `400` | `INVALID_ENVELOPE` | 字段、类型、枚举、条件必填或结构化数据不合规；修正载荷后使用正确身份重报 |
| `404` | `COMMAND_NOT_FOUND` | 仅结果回调；仓库执行系统不认识该 `command_code`，不推进业务 |
| `409` | `IDEMPOTENCY_CONFLICT` | 同一幂等身份对应不同载荷；停止自动重报并人工对账 |
| `409` | `RESULT_BEFORE_DISPATCH` | 仅结果回调；命令尚未下发却收到结果，仓库执行系统封锁命令并进入人工对账，禁止自动重报或重新下发 |
| `413` | `PAYLOAD_TOO_LARGE` | 超过 `256 KiB`；缩小载荷后按正确身份重报 |
| `503` | `TEMPORARILY_UNAVAILABLE` | 仓库执行系统尚未持久接收，设备控制系统可保留原载荷延后重报 |

`INVALID_ENVELOPE` 示例：

```json
{
  "code": 400,
  "message": "INVALID_ENVELOPE",
  "error_detail": {
    "issues": [
      {
        "field": "data",
        "code": "INVALID_TYPE",
        "expected": "object"
      }
    ]
  }
}
```

稳定错误码是含义固定、可供设备控制系统编程判断的代码：`INVALID_JSON` 表示正文不是合法结构化数据，
`FIELD_REQUIRED` 表示缺少必填字段，`INVALID_TYPE` 表示类型错误，`EXTRA_FORBIDDEN` 表示出现不允许的字段，
`INVALID_VALUE` 表示字段值不在合同允许范围内。

字段路径用 `$` 表示整个结构化数据根对象，用点号表示嵌套关系，例如 `error_detail.code`。结果回调和事件回调的顶层扩展字段会被忽略，
不产生 `EXTRA_FORBIDDEN`。`error_detail` 仍是闭集；为避免回显供应商传入的未知字段名，其中的未知字段统一写作
`error_detail.<extra>`。一个请求有多个错误时，仓库执行系统可以在 `issues` 数组中一次返回多项。

仓库执行系统首次成功接收并保存后，再收到完全相同的结果回调或事件回调，仍返回相同的 `200 ACK`，但只处理一次。
设备控制系统如果没有收到确定的 `200 ACK`，可以重报完全相同的回调；收到 `409` 后不能更换身份绕过冲突。

如果命令尚未下发就收到结果回调，仓库执行系统返回 `RESULT_BEFORE_DISPATCH`。之后即使设备控制系统重报完全相同的提前结果，
仓库执行系统仍返回同一错误。这个响应不能证明设备已经完成动作。设备控制系统和仓库执行系统都不能自动重新下发，现场人员
必须核对设备事实以及双方记录。

## 5. 实施与验收清单

本章把前面的接口约定整理成执行顺序，不增加任何接口字段。

### 5.1 设备控制系统（ECS）供应商实施

1. 按第 3 章提供固定的作业指令和状态查询方法、路径、请求结构和响应结构。
2. 为每类设备编写设备合同附录，明确 `task_type`、`params`、`event_type` 和 `data` 的二级字段。
3. 使用 `command_code` 实现幂等。相同身份和相同载荷不能重复驱动设备，相同身份和不同载荷必须返回冲突。
4. 把作业指令接收确认、设备执行和结果回调分开实现。返回 `ACK` 后，仍需在动作结束时回调结果。
5. 设备主动发生事件时调用事件回调。未收到确定 `200 ACK` 时，只能重报完全相同的回调。
6. 按错误表实现协议状态、`message` 和重报策略。交付结果未知时停止自动重放，转人工对账。

### 5.2 仓库执行系统（WES）开发与部署

1. 为设备控制系统配置可访问的基础地址，并为设备控制系统配置可反向访问的仓库执行系统回调基础地址。
2. 按设备合同附录组装作业指令 `params`，并解析结果回调和事件回调的 `data`；不得增加顶层私有字段。
3. 发送作业指令前查询设备状态。状态不可信或不满足准入条件时失败关闭。
4. 联调记录分别标明作业指令已发送、设备控制系统已接纳、结果回调已收到和事件回调已收到，不得用一个状态代替其他状态。
5. 遇到交付结果未知、幂等冲突或提前结果时停止自动重发并人工对账，不能更换身份绕过已有结果。

### 5.3 联调验收分层

现场报告应写清楚实际证明了哪一层，不能把较低层的成功写成整条链路完成。

| 验收层 | 需要看到的证据 | 这一层不能证明什么 |
| --- | --- | --- |
| 网络可达 | 仓库执行系统能访问设备控制系统，设备控制系统也能访问仓库执行系统回调地址 | 不能证明结构化数据字段正确或设备会动作 |
| 合同接受 | 四个接口按本文接受请求并返回规定的状态码和结构化数据 | 不能证明设备控制系统已可靠接纳某条作业指令 |
| 命令接纳 | 仓库执行系统收到完全符合第 3.1 节的 `200 ACK` | 不能证明设备已完成物理动作 |
| 结果闭环 | 仓库执行系统收到与 `command_code` 匹配的结果回调，并返回 `200 ACK` | 不能代替事件回调链路或真实设备验收 |
| 事件闭环 | 仓库执行系统收到事件回调，保存回调并返回 `200 ACK` | 不能证明某条作业指令已完成 |
| 真实设备验收 | 现场核对设备事实与结果回调，确认动作结果一致 | 不能证明仓库管理系统、产线流程或整体业务已经完成验收 |
| 业务验收 | 正式业务流程根据完整事实产生预期业务决策 | 设备接口通过、单次物理动作成功或本地模拟测试都不能代替这一层 |
