# SMT 粗分机联调手册（供应商版）

> 面向设备侧开发、现场调试与联调验收。
> 适用系统：WES 后端 / SMT 粗分机插件 `rough_sorter.v2`。
> 适用设备：粗分机入料机械臂、输送线、出料机械臂。
> 文档版本：v1.2。
> 最近同步：2026-07-31，同步 Q19 前置准入与 SCAN 测量字段；供应商版只保留真实协议联调口径。

---

## 0. 快速联调路径

先按这个顺序跑。不要一开始就接真实设备；网络、签名、设备动作混在一起时，排障会很慢。

1. WES 项目组开通硬件方账号和设备管理权限。
2. 硬件方在本系统管理界面维护设备主数据：`device_code`、角色、`host`、`port`、`protocol`、`callback_path`、`status_path`。
3. 硬件方实现设备状态接口，确保 WES 查询时能看到命令目标设备处于 `AUTO` / `IDLE`。
4. 硬件方用 `curl` 调通 `POST /api/v1/callback/event`，确认 API 签名正确。
5. 现场触发 `WORKLINE_START_REQUESTED`，START 准入通过后 WorkLine 从 `STOPPED` 进入 `READY`。
6. WES 按设备基础数据里的 `{protocol}://{host}:{port}{callback_path}` 下发命令，硬件方对照命令包络实现设备命令接收服务。
7. 硬件方设备收到 WES 命令后先返回 HTTP 200 ACK，不在 ACK 阶段执行长耗时动作。
8. 设备动作完成后调用 `POST /api/v1/callback/result` 回传 Result。
9. 双方通过 Trace 核对 Session、Command、Outbox、Inbox、Timeline 是否推进到预期状态。

本文中涉及三类调用方式：

| 调用方向 | 接口 | 认证方式 | 用途 |
| --- | --- | --- | --- |
| 设备 -> WES | `/api/v1/callback/event`、`/api/v1/callback/result` | `APP_ID` / `APP_SECRET` 签名 | 真实设备上报事件和结果 |
| WES -> 设备 | `{protocol}://{host}:{port}{callback_path}` | 当前默认不带签名 Header | WES 下发设备动作命令 |
| WES -> 设备 | `{protocol}://{host}:{port}{status_path}` | 当前默认不带签名 Header | START 准入和命令派发前查询设备实时状态 |

WES 内部无真实设备调试使用 Sandbox / Mock ECS，不属于供应商正式联调路径；内部操作见
[`粗分机内部Mock与Sandbox调试手册.md`](./粗分机内部Mock与Sandbox调试手册.md)。

## 1. 联调目标

这份文档只说明粗分机和 WES 的 HTTP 对接。联调时重点看这几件事：

- 设备向 WES 上报扫码事件。
- 现场 START 触发后，WES 能确认所有命令目标设备可接收任务。
- WES 向设备下发粗分机动作命令。
- 设备返回 HTTP ACK。
- 设备执行完成后回传 Result。
- 业务 NG 与硬件失败的区分。
- 使用 Trace 接口定位联调问题。

粗分机正常主路径：

```text
现场 START
  -> WorkLine READY
  -> SCAN_COMPLETED
  -> 扫码/测量事实归一化
  -> Q19 准入 ADMIT 并持久化
  -> PICK_AND_PUT
  -> 测量值校验
  -> MOVE_FORWARD
  -> 出料料格分配
  -> PUT_TO_BIN
  -> CONSUME_BIN_CELL + MATERIAL_MOUNTED
  -> Session COMPLETED
```

业务 NG 路径：

```text
SCAN_COMPLETED 条码 NG 或 Q19 REJECT
  -> MARK_NG
  -> MOVE_TO_NG
  -> Session COMPLETED
```

物理失败路径：

```text
任一设备动作 FAILED、设备状态不可信、出料分配冲突、PUT_TO_BIN 失败
  -> RuntimeHold / blocking-point
  -> 人工确认设备和物料状态

Q19 provider timeout/unavailable
  -> WES 在任何正常入料命令前 fail-closed
  -> 当前返回失败并保留 provider failure evidence
  -> T6 尚未闭环 Session Hold，设备侧不会收到补偿命令
```

### 1.1 完整物理工作流程

下面是当前 `rough_sorter.v2` 的完整工作流程口径。供应商实现设备程序时，重点关注“设备收到什么命令、什么时候回 Result、哪些情况算业务 NG、哪些情况算设备失败”。

| 阶段 | 触发方 | WES 行为 | 设备侧动作 | 下一步 |
| --- | --- | --- | --- | --- |
| 现场启动 | 入料臂或现场 START 按钮 | 接收 `WORKLINE_START_REQUESTED`，检查 WorkLine 配置和所有命令目标设备实时状态 | 状态接口返回 `AUTO` / `IDLE` / `current_command_id=null` | 准入通过后 WorkLine 进入 `READY` |
| 扫码与 Q19 准入 | 入料臂或扫码点 | 接收 `SCAN_COMPLETED`，归一化扫码与顶层 `reel_diameter_mm` / `reel_thickness_mm` 后先执行 Q19；只有 `ADMIT` typed decision 持久化后才生成正常入料命令 | 上报六合一码与两个必填测量字段 | `ADMIT` 后下发 `PICK_AND_PUT`；`REJECT` 由输入臂走 NG；timeout/unavailable 不下发物理命令，当前 fail-closed，T6 尚未闭环 Session Hold |
| 入料搬运与测量 | WES 下发给 `ROUGH_SORTER_INPUT_ARM` | 复用已持久化的 Q19 `ADMIT`，生成 `PICK_AND_PUT`，目标位置为输送线入料位 | 入料臂从扫码/检测位取料并放到输送线入料位，动作完成后回传 Result；若回传测量值，WES 继续做结果合同校验 | 结果有效后下发 `MOVE_FORWARD`；不得在此阶段重新执行 Q19 |
| 输送前进 | WES 下发给 `ROUGH_SORTER_CONVEYOR` | 生成 `MOVE_FORWARD`，从输送线入料位移动到出料位 | 输送线将物料移动到出料位，完成后回传 Result | WES 开始出料料格分配 |
| 出料分配 | WES 资源域 | 查询 active bin rack，调用料格分配策略，先预约目标料格 | 设备侧无动作 | 分配成功下发 `PUT_TO_BIN`；需要换架则等待 WMS/RCS 到架；资源阻塞进入 Hold |
| 出料入箱 | WES 下发给 `ROUGH_SORTER_OUTPUT_ARM` | 生成 `PUT_TO_BIN`，携带目标 `bin_location` | 出料臂从出料位取料并放入目标料箱格位 | 成功后 WES 消费预约、写入物料入箱事实并完成 Session |
| NG 搬运 | WES 下发给 `ROUGH_SORTER_INPUT_ARM` | 对业务 NG 先记录 `MARK_NG`，再生成 `MOVE_TO_NG` | 入料臂把当前物料移动到 NG 位 | 成功后完成 Session；失败进入 Hold |

### 1.2 START 到 READY

粗分机默认不直接接收生产事件。WorkLine 处于 `STOPPED` 时，只接受 START 控制事件；`SCAN_COMPLETED` 等生产事件会被快速拒收。

START 通过必须同时满足：

- WorkLine 已绑定粗分机插件 `rough_sorter`。
- 三类设备角色都存在且绑定到当前 WorkLine：入料臂、输送线、出料臂。
- 每台命令目标设备都配置了可访问的 `host`、`port`、`protocol`、`callback_path` 和 `status_path`。
- 设备实时状态接口返回 `mode=AUTO`、`status=IDLE`、`current_command_id=null`。

START 通过后，WorkLine 进入 `READY`，才开始接收 `SCAN_COMPLETED`。如果 START 失败，先按 `reason_code` 处理设备状态、网络、配置或绑定问题，不要直接重放扫码事件。

### 1.3 扫码、Session 与业务主键

扫码完成后，设备调用 `POST /api/v1/callback/event` 上报 `SCAN_COMPLETED`。六合一码放在 `data`，Q19 必需的测量值放在事件顶层：

- `HHPN`：物料编码/SKU。
- `MfrPN`：制造商料号。
- `Qty`：数量。
- `DateCode`：日期码。
- `LotCode`：批次。
- `PkgID`：包号/载具唯一号，粗分机 Session 的业务主键来源。
- `reel_diameter_mm`：卷盘直径，正数，事件顶层必填。
- `reel_thickness_mm`：卷盘厚度，正数，事件顶层必填。

`PkgID` 必须稳定、唯一、非空。同一 `PkgID` 的重复事件用于幂等和恢复，不应被设备侧随意重写。

扫码后 WES 会先做条码业务判定，并在任何正常入料命令前完成 Q19：

- 条码字段完整且未命中 NG 规则：以归一化扫码/测量事实执行 Q19。
- Q19 `ADMIT` typed decision 已持久化：写入 Session 上下文，阶段进入 `PICK_TO_PIPELINE`，下发 `PICK_AND_PUT`。
- Q19 `REJECT`：记录 NG 原因，输入臂直接下发 `MOVE_TO_NG`，不得先执行 `PICK_AND_PUT`。
- Q19 timeout/unavailable：保持 `READY`，通用 fail-closed 返回失败并保留 provider failure evidence，不下发任何物理命令；T6 尚未形成 Session Hold。
- 条码无效、不完整或命中业务 NG 规则：记录 NG 原因，阶段进入 `NG_MOVING`，下发 `MOVE_TO_NG`。

### 1.3.1 多物料并发与资源等待

同一条 WorkLine 可以同时存在多个未完成 Session。`SCAN_COMPLETED` 进入 WES 后仍按 Inbox 到达顺序建链路，但后续推进速度由真实资源决定，不由工作线级开关决定。

并发容量来自这些事实：

- 目标设备是否空闲。
- Station、输送位、出料位、active rack、料箱和格位是否可用。
- 外部 WMS/RCS operation 是否已经完成或可继续。

设备侧不需要关心 WES worker 的 `limit` 或内部调度参数；这些参数只影响 WES 单轮处理多少条消息，不代表工作线能同时跑几盘料。

如果某个物料的下一步资源暂时不可用，WES 会记录 `RESOURCE_WAIT` 诊断并等待重试。供应商排障时重点看诊断中的 `resource_kind`、`resource_key`、首次等待时间、最近等待时间和等待次数。`RESOURCE_WAIT` 不等于设备失败，设备侧不要为了“解除等待”伪造成功或失败 Result。

设备命令完成和 WES 本地设备状态投影只用于 Trace 和诊断展示。被设备忙挡住的 Outbox 必须等下一轮真实设备状态接口返回 `IDLE` 后才会重新派发；本地投影为 `IDLE` 不直接代表派发放行。

`WORKLINE_ENTRY_ADMISSION_BLOCKED` 不再是新运行过程的正常诊断。如果现场 Trace 中看到它，应按历史数据或旧版本残留处理，不要作为当前并发容量调参依据。

### 1.4 Q19 后的入料搬运与测量结果

`PICK_AND_PUT` 是入料臂命令。设备收到命令后要先快速返回 HTTP 200 ACK，然后执行物理动作：

1. 从 `params.source_location` 指定的扫码/检测位取料。
2. 放到 `params.target_location` 指定的输送线入料位，默认是 `PIPELINE-IN-01`。
3. 如双方协议要求，完成搬运后的复测。
4. 调用 `/api/v1/callback/result` 回传动作结果；复测数据仅用于结果合同校验，不触发新的 Q19。

成功 Result 至少要带：

```json
{
  "data": {
    "reel_diameter": "178.0",
    "reel_thickness": "15.0"
  }
}
```

Q19 已在 `PICK_AND_PUT` 前完成并持久化。WES 对 `PICK_AND_PUT SUCCESS` 的处理顺序固定：

1. 校验 `reel_diameter` 和 `reel_thickness` 是否存在、可解析、为正数。
2. 检查 `measurement_result`、`inspection_result`、`size_judgement`、`thickness_judgement` 是否为 `NG`。
3. 复用当前 Session 已持久化的 Q19 `ADMIT`，生成 `MOVE_FORWARD`；禁止在这里重新查询 Q19。

测量字段缺失、不可解析、非正数，或测量判定字段为 `NG`，当前都按测量合同对应的业务 NG/Hold 规则处理。Q19 的 WMS 业务拒绝已经在入料动作前转为输入臂 NG；Q19 不可用、超时、熔断或响应不可解析也已经在入料动作前进入 Hold，不得先搬运后补判。

如果 `PICK_AND_PUT` 物理动作失败，例如取料失败、夹爪报警、物料位置不确定，设备必须回 `FAILED + error_detail`。这类失败不会走业务 NG，WES 会阻断当前物料并要求人工确认。

### 1.5 输送线前进

入料结果有效且已持久化 Q19 `ADMIT` 后，WES 向输送线下发 `MOVE_FORWARD`：

- `source_location` 默认是 `PIPELINE-IN-01`。
- `target_location` 默认是 `PIPELINE-OUT-01`。
- Result 成功时不要求回传测量值。

`MOVE_FORWARD SUCCESS` 后，WES 不会立即完成流程，而是进入出料分配。`MOVE_FORWARD FAILED` 表示输送动作失败或物料位置不可信，WES 会进入 Hold，不会自动下发 `PUT_TO_BIN` 或 `MOVE_TO_NG`。

### 1.6 出料分配与货架等待

输送线把物料送到出料位后，WES 会在资源域中为当前 `PkgID` 规划目标料箱格位。

分配结果有三类：

| 分配结果 | WES 行为 | 设备侧影响 |
| --- | --- | --- |
| `ALLOCATED` | 写入 `CLAIM_BIN_CELL` 预约，阶段进入 `PUTTING_TO_BIN`，下发 `PUT_TO_BIN` | 出料臂收到目标 `bin_location` 后执行入箱 |
| `RACK_OPERATION_REQUIRED` | 阶段进入 `WAITING_RACK`，向 WMS/RCS 发起换架或补架 operation | 粗分机设备等待，不会收到新的出料命令 |
| `BLOCKED` 或无可执行决策 | 写 blocking-point / RuntimeHold | 由 WES 项目组处理资源配置、料箱、料格或投影问题 |

当需要换架或补架时，WES 会等待外部回调：

```text
WMS operation-specific typed terminal result
  -> 写 RACK_ARRIVED / BIN_MOUNTED 资源事实
  -> 创建内部 ROUGH_SORTER_STORAGE_RETRY 事件
  -> 重新执行出料分配
  -> 分配成功后下发 PUT_TO_BIN
```

这一步是两阶段恢复：外部回调先落资源事实，再由内部重试事件重新分配料格。供应商设备侧一般不需要处理 `ROUGH_SORTER_STORAGE_RETRY`，只需要等待后续 `PUT_TO_BIN` 命令。

### 1.7 出料入箱与完成

`PUT_TO_BIN` 是出料臂命令。设备按 `params.bin_location` 将物料放入目标料箱格位。

`PUT_TO_BIN SUCCESS` 后，WES 会执行终态写入：

- 消费前面预约的目标料格：`CONSUME_BIN_CELL`。
- 写入物料挂载事实：`MATERIAL_MOUNTED`。
- 记录 `PkgID`、物料编码、批次、日期码、测量值和目标料箱格位。
- 将当前 Session 标记为 `COMPLETED`。

`PUT_TO_BIN FAILED` 时，WES 默认保留料格预约并进入 Hold。原因是出料失败后系统无法确认物料是否仍在出料位、是否已经部分放入料箱、是否需要人工复位；设备侧不要通过业务 NG 规避这种物理不确定状态。

### 1.8 NG 与 Hold 的边界

供应商联调时最容易混淆的是“业务 NG”和“设备失败”。按下面规则处理：

| 类型 | 示例 | Result 表达 | WES 行为 |
| --- | --- | --- | --- |
| 业务 NG | 条码不完整、命中扫码 NG 规则、Q19 `REJECT`、测量判定 NG | Q19 `REJECT` 由 WES 在命令前判定；设备只执行随后收到的 NG 语义命令 | `MARK_NG -> MOVE_TO_NG -> COMPLETED` |
| 设备失败 | 取料失败、输送失败、放置失败、夹爪报警、位置不确定、急停、硬件异常 | `result=FAILED`，必须带 `error_detail` | RuntimeHold / blocking-point，人工处理 |
| 外部依赖不可用 | Q19 provider 超时/不可用、响应不可解析、资源分配冲突 | 不由设备伪造成功或失败 | Q19 当前在命令前 fail-closed 且 T6 尚未闭环 Session Hold；其他资源问题按对应 blocking-point 处理 |

简单判断：如果设备动作本身已经完成，只是业务规则判定这盘料不能入箱，走业务 NG；如果设备动作没有完成或物理位置不可信，走 `FAILED`；如果 WES 依赖或资源域不满足，等待 WES 侧诊断，不要由设备侧补造结果。

本文中的 `PICK_AND_PUT`、`MOVE_FORWARD`、`MOVE_TO_NG` 是 WES 语义动作槽位，用于说明顺序和回调责任，不冻结供应商真实 `task_type`、`params` 或厂商私有命令字段。真实协议映射必须以双方另行批准的设备协议为准。

## 3. API 签名认证

正式联调环境使用 API App 签名。开发环境如果 WES 临时打开 `SKIP_API_AUTH=True`，可以跳过签名；供应商程序仍按正式签名实现。

### 3.1 请求 Header

| Header | 必填 | 说明 |
| --- | --- | --- |
| `X-App-ID` | 是 | WES 分配给供应商或设备系统的应用 ID |
| `X-Timestamp` | 是 | Unix 秒级时间戳 |
| `X-Signature` | 是 | HMAC-SHA256 小写十六进制签名 |
| `Content-Type` | 是 | 固定为 `application/json` |

### 3.2 签名规则

签名原文：

```text
{app_id}{timestamp}{HTTP_METHOD}{request_path}
```

规则：

- `HTTP_METHOD` 使用大写，例如 `POST`。
- `request_path` 只包含路径，例如 `/api/v1/callback/result`。
- 签名不包含 body，避免 JSON 序列化差异导致验签失败。
- `X-Timestamp` 放在 WES 当前时间前后可接受窗口内。
- `APP_SECRET` 只放在本机环境变量或设备安全配置里，不要写进代码、工单、群聊截图、日志或长期留存文档。

Bash 示例：

```bash
APP_ID="app_7hBRU_aYUnM8ZY2S"
APP_SECRET="<由 WES 项目组通过安全渠道提供>"
TS=$(date +%s)
METHOD="POST"
PATH="/api/v1/callback/result"

SIGN=$(printf "%s" "${APP_ID}${TS}${METHOD}${PATH}" \
  | openssl dgst -sha256 -hmac "$APP_SECRET" -hex \
  | awk '{print $2}')
```

联调时可以先定义一个函数，后面 Event 和 Result 请求都能复用：

```bash
sign_wes_request() {
  local method="$1"
  local path="$2"
  local ts="$3"

  printf "%s" "${APP_ID}${ts}${method}${path}" \
    | openssl dgst -sha256 -hmac "$APP_SECRET" -hex \
    | awk '{print $2}'
}
```

## 4. 粗分机设备角色

粗分机工作线需要三类设备。少任意一类，后续命令都会卡住。

| 设备角色 | 测试 `device_code` | 支持事件/命令 | 说明 |
| --- | --- | --- | --- |
| `ROUGH_SORTER_INPUT_ARM` | `RS-INPUT-ARM-01` | `SCAN_COMPLETED`, `PICK_AND_PUT`, `MOVE_TO_NG` | 入料机械臂，负责扫码入口、入线抓取、测量回传和 NG 搬运 |
| `ROUGH_SORTER_CONVEYOR` | `RS-CONVEYOR-01` | `MOVE_FORWARD` | 输送线，负责将物料从入料端移动到出料端 |
| `ROUGH_SORTER_OUTPUT_ARM` | `RS-OUTPUT-ARM-01` | `PUT_TO_BIN` | 出料机械臂，负责将物料放入目标料箱格位 |

联调前先准备这些信息，并由硬件方在本系统管理界面维护到对应设备基础信息中：

- 每台设备的 `host`、`port`、`protocol`、`callback_path`。
- 每台设备的状态查询路径 `status_path`，不填时默认 `/api/v1/device/status`。
- 每台设备支持的 `task_type` 清单。
- 最大并发、超时时间、幂等策略。
- 设备错误码字典。

`host`、`port`、`protocol`、`callback_path` 是 WES 下发命令时使用的设备连接配置。`status_path` 是 WES 查询设备实时状态时使用的路径。硬件方负责在本系统管理界面自行维护；WES 项目组负责开通账号权限、确认字段口径和联调结果。

`callback_path` 是设备基础信息里的命令接收路径。不填时，WES 使用默认路径 `/api/v1/device/command`。
`status_path` 建议放在设备能力配置中，例如 `capabilities.status_path=/api/v1/device/status`；不填时，WES 使用默认路径 `/api/v1/device/status`。

例如供应商服务地址是 `http://10.0.0.10:9000/api/device/command`，设备主数据填：

| 字段 | 示例 |
| --- | --- |
| `protocol` | `HTTP` |
| `host` | `10.0.0.10` |
| `port` | `9000` |
| `callback_path` | `/api/device/command` |
| `status_path` | `/api/v1/device/status` |

### 4.1 设备实时状态接口

START 准入和真实命令派发前，WES 会查询设备实时状态：

```text
GET {protocol}://{host}:{port}{status_path}?device_code={device_code}
```

单设备响应示例：

```json
{
  "device": {
    "device_code": "RS-CONVEYOR-01"
  },
  "state": {
    "device_code": "RS-CONVEYOR-01",
    "mode": "AUTO",
    "status": "IDLE",
    "current_command_id": null
  }
}
```

批量状态响应也可以用于 START 准入：

```json
{
  "devices": [
    {
      "device": {
        "device_code": "RS-INPUT-ARM-01"
      },
      "state": {
        "mode": "AUTO",
        "status": "IDLE",
        "current_command_id": null
      }
    }
  ]
}
```

准入要求：

- `mode` 必须为 `AUTO`。
- `status` 必须为 `IDLE`。
- `current_command_id` 必须为空。
- 响应必须包含目标 `device_code`。

如果状态接口超时、非 2xx、JSON 格式不符合要求，或者任一命令目标设备不是 `AUTO` / `IDLE`，WES 会拒绝 START 或拒绝派发命令。现场表现通常是 HTTP 409、Trace blocking-point 或 START 准入失败信息。

### 4.2 WorkLine START 准入

当前 WorkLine 运行态口径：

| 运行态 | 含义 | 对设备事件的影响 |
| --- | --- | --- |
| `STOPPED` | 等待现场 START | 不接收 `SCAN_COMPLETED` 等生产事件，只接收 START 控制事件 |
| `READY` | 已通过 START 准入 | 可以接收生产事件并推进粗分机流程 |
| `RECONCILING` | 运行时对账隔离中 | 不接收生产事件，待人工处理后回到 `STOPPED` |
| `ESTOPPED` | 急停冻结中 | 不接收生产事件，需人工清除急停后回到 `STOPPED` |

真实现场 START 使用设备事件接口：

```text
POST /api/v1/callback/event
```

请求示例：

```json
{
  "device_code": "RS-INPUT-ARM-01",
  "event_type": "WORKLINE_START_REQUESTED",
  "timestamp": 1777200000000,
  "trace_id": "trace-start-rough-sorter-0001",
  "event_id": "evt-start-0001",
  "data": {
    "operator": "field-start-button"
  }
}
```

START 准入通过后，WES 返回 HTTP 200，WorkLine 进入 `READY`，并释放因 `STOPPED` 停放的待派发命令。START 事件可幂等重试；如果 WorkLine 已经是 `READY`，WES 按已完成 START 处理。

START 准入失败时，WES 返回 HTTP 409，响应 `data.reason_code` 会说明原因。常见值：

| `reason_code` | 含义 | 处理建议 |
| --- | --- | --- |
| `START_ADMISSION_DEVICE_CONTEXT_INVALID` | 设备上下文解析失败 | 检查 `device_code` 是否存在并绑定 WorkLine |
| `START_ADMISSION_WORKLINE_NOT_BOUND` | 设备未绑定 WorkLine | 在设备主数据中绑定正确 WorkLine |
| `START_ADMISSION_CONFIGURATION_INVALID` | WorkLine 配置预检失败 | 检查角色、能力、通信配置和 `status_path` |
| `START_ADMISSION_DEVICE_STATUS_MISSING` | 状态接口未返回目标设备 | 确认 status 响应包含所有命令目标设备 |
| `START_ADMISSION_DEVICE_NOT_IDLE` | 设备不是 `AUTO` / `IDLE` 或仍有关联命令 | 现场复位设备，清空未完成命令后重试 START |
| `START_ADMISSION_ECS_TIMEOUT` | 状态接口超时 | 检查 WES 到设备网络、端口和服务响应时间 |

## 5. 设备上报 Event 协议

### 5.1 `SCAN_COMPLETED` 扫码完成事件

扫码完成后，设备调用：

```text
POST /api/v1/callback/event
```

业务字段放在 `data` 里，不要把六合一码字段放到顶层。

`PkgID` 是粗分机的业务主键。这个值要稳定、唯一、非空。

| 字段 | 位置 | 必填 | 说明 |
| --- | --- | --- | --- |
| `device_code` | 顶层 | 是 | 上报设备编码，必须能在 WES 中路由到对应 WorkLine |
| `event_type` | 顶层 | 是 | 固定为 `SCAN_COMPLETED` |
| `timestamp` | 顶层 | 建议 | Unix 毫秒时间戳 |
| `trace_id` | 顶层 | 建议 | 链路追踪 ID，现场排障用 |
| `event_id` | 顶层 | 建议 | 供应商事件唯一 ID，用于幂等和审计 |
| `data.HHPN` | `data` | 是 | 物料编码/SKU |
| `data.MfrPN` | `data` | 是 | 制造商料号 |
| `data.Qty` | `data` | 是 | 数量 |
| `data.DateCode` | `data` | 是 | 日期码 |
| `data.LotCode` | `data` | 是 | 批次 |
| `data.PkgID` | `data` | 是 | 包号/载具唯一号，粗分机业务主键来源 |
| `reel_diameter_mm` | 顶层 | 是 | Q19 使用的卷盘直径，必须为正数 |
| `reel_thickness_mm` | 顶层 | 是 | Q19 使用的卷盘厚度，必须为正数 |
| `data.location` | `data` | 建议 | 扫码/测量位置 |

请求示例：

```bash

METHOD="POST"

curl -sS -X POST "$WES_API/callback/event" \
  -H "Content-Type: application/json" \
  -H "X-App-ID: $APP_ID" \
  -H "X-Timestamp: $TS" \
  -H "X-Signature: $SIGN" \
  -d '{
    "device_code": "RS-INPUT-ARM-01",
    "event_type": "SCAN_COMPLETED",
    "timestamp": 1777200000000,
    "trace_id": "trace-rough-sorter-0001",
    "event_id": "evt-scan-0001",
    "reel_diameter_mm": "178.0",
    "reel_thickness_mm": "15.0",
    "data": {
      "location": "ARM01",
      "HHPN": "CAP001",
      "MfrPN": "V0001-CAP-0402",
      "Qty": "100",
      "DateCode": "20260409",
      "LotCode": "LOT-A",
      "PkgID": "PKG-CAP001-LOT-A-001"
    }
  }'
```

返回示例：

```json
{
  "code": 200,
  "data": {
    "request_id": "...",
    "trace_id": "trace-rough-sorter-0001",
    "event_id": "evt-scan-0001",
    "causation_id": null
  }
}
```

说明：HTTP 200 只表示 WES 已接收事件，不表示整条工作线已经完成。

## 6. WES 下发设备 Command 协议

WES 按设备主数据拼出命令地址，然后发送 HTTP POST：

```text
{protocol}://{host}:{port}{callback_path}
```

默认 `callback_path`：

```text
/api/v1/device/command
```

WES 下发设备命令时，不带 `X-App-ID` / `X-Signature` 这组回调签名 Header。WES 只按设备主数据中的地址发 HTTP POST。设备侧如果要求认证、白名单、网关 Token 或 mTLS，联调前先和 WES 项目组约定，否则设备可能直接拒收命令。

真实命令派发前，WES 会先查询目标设备状态接口。只有目标设备实时状态为 `AUTO` / `IDLE` 且 `current_command_id` 为空时，才会继续 POST 命令。这个预检用于避免设备已经在动作中时重复产生物理副作用。

### 6.1 ACK 规则

WES 以设备返回 HTTP 200 作为 ACK 成功。

设备可以返回：

```json
{
  "code": 200,
  "message": "OK",
  "trace_id": "device-local-log-20260530-001"
}
```

非 200、网络异常或超时会触发 WES 重试和诊断。

### 6.2 通用 Command 包络

设备程序只按 `command_code`、`task_type`、`params` 解析动作。`priority`、`timeout`、`timestamp` 是调度辅助字段，可以记日志或做超时处理，不要用它们决定业务动作。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `device_code` | 是 | WES 命令目标设备编码，Result 必须使用同一个设备编码回传 |
| `command_code` | 是 | WES 生成的全局唯一命令号，Result 原样回传 |
| `task_type` | 是 | 命令类型 |
| `params` | 是 | 业务参数对象 |
| `priority` | 辅助 | 命令优先级 |
| `timeout` | 辅助 | WES 给出的超时时间，单位毫秒 |
| `timestamp` | 辅助 | WES 下发时间，Unix 毫秒 |

### 6.3 粗分机 `task_type`

| `task_type` | 目标设备角色 | `params` 核心字段 | 完成后下一步 |
| --- | --- | --- | --- |
| `PICK_AND_PUT` | `ROUGH_SORTER_INPUT_ARM` | `business_key`, `source_location`, `target_location`, `six_in_one`, `trace_id` | Q19 已在命令前完成；成功 Result 回报动作结果，若附复测值仅用于结果合同校验 |
| `MOVE_FORWARD` | `ROUGH_SORTER_CONVEYOR` | `business_key`, `source_location`, `target_location` | 成功后 WES 尝试分配料箱；分配成功才下发 `PUT_TO_BIN` |
| `PUT_TO_BIN` | `ROUGH_SORTER_OUTPUT_ARM` | `business_key`, `source_location`, `target_location`, `bin_location` | 成功后 WES 完成 Session 并记录资源事实 |
| `MOVE_TO_NG` | `ROUGH_SORTER_INPUT_ARM` | `business_key`, `source_location`, `target_location`, `ng_location`, `reason_code` | 成功后完成当前物料流程 |

### 6.4 `PICK_AND_PUT` 入料命令示例

```json
{
  "device_code": "RS-INPUT-ARM-01",
  "command_code": "CMD-20260530-PICK_AND_PUT-ABC12345",
  "task_type": "PICK_AND_PUT",
  "params": {
    "business_key": "PKG-CAP001-LOT-A-001",
    "source_location": "SCAN_STATION",
    "target_location": "PIPELINE-IN-01",
    "six_in_one": {
      "HHPN": "CAP001",
      "MfrPN": "V0001-CAP-0402",
      "Qty": "100",
      "DateCode": "20260409",
      "LotCode": "LOT-A",
      "PkgID": "PKG-CAP001-LOT-A-001"
    },
    "trace_id": "trace-rough-sorter-0001"
  }
}
```

## 7. 设备回传 Result 协议

设备完成动作后调用：

```text
POST /api/v1/callback/result
```

### 7.1 Result 字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `command_code` | 是 | 必须等于 WES 下发命令中的 `command_code` |
| `device_code` | 是 | 执行该命令的设备编码，必须与 WES 命令目标设备一致 |
| `result` | 是 | `SUCCESS` 或 `FAILED` |
| `finish_time` | 是 | Unix 毫秒完成时间 |
| `data` | `SUCCESS` 时建议 | 业务结果数据 |
| `error_detail` | `FAILED` 时必填 | 设备动作失败、硬件异常、位置不确定等错误详情 |
| `trace_id` / `event_id` / `causation_id` | 建议 | 链路追踪字段 |

排障和补偿时先看 `command_code`。设备即使没有回传 `trace_id`，WES 也会按 `command_code` 找回上下文。

### 7.2 `PICK_AND_PUT` 成功并回传测量值示例

```bash
PATH="/api/v1/callback/result"
METHOD="POST"
TS=$(date +%s)
SIGN=$(sign_wes_request "$METHOD" "$PATH" "$TS")

curl -sS -X POST "$WES_API/callback/result" \
  -H "Content-Type: application/json" \
  -H "X-App-ID: $APP_ID" \
  -H "X-Timestamp: $TS" \
  -H "X-Signature: $SIGN" \
  -d '{
    "command_code": "CMD-20260530-PICK_AND_PUT-ABC12345",
    "device_code": "RS-INPUT-ARM-01",
    "result": "SUCCESS",
    "finish_time": 1777200060000,
    "trace_id": "trace-rough-sorter-0001",
    "event_id": "evt-measure-result-0001",
    "data": {
      "reel_diameter": "178.0",
      "reel_thickness": "15.0"
    }
  }'
```

### 7.3 测量业务 NG

设备动作成功，但检测结果判定为 NG 时，不要回 `FAILED`。

回 `SUCCESS`，在 `data` 里带业务 NG 字段。

```json
{
  "command_code": "CMD-20260530-PICK_AND_PUT-ABC12345",
  "device_code": "RS-INPUT-ARM-01",
  "result": "SUCCESS",
  "finish_time": 1777200060000,
  "data": {
    "reel_diameter": "178.0",
    "reel_thickness": "15.0",
    "inspection_result": "NG",
    "ng_reason": "INSPECTION_SIZE_NG"
  }
}
```

下面任一字段为 `NG`，WES 都按业务 NG 处理：

- `measurement_result`
- `inspection_result`
- `size_judgement`
- `thickness_judgement`

之后 WES 会生成业务 NG，并下发 `MOVE_TO_NG`。

### 7.4 设备动作失败

只有设备未完成动作、位置不确定、抓取失败、放置失败、硬件报警等情况，才回 `FAILED`。

```json
{
  "command_code": "CMD-20260530-PICK_AND_PUT-DEF67890",
  "device_code": "RS-INPUT-ARM-01",
  "result": "FAILED",
  "finish_time": 1777200090000,
  "error_detail": {
    "code": "PICK_AND_PUT_FAILED",
    "message": "夹爪取料失败，物料位置不确定",
    "retryable": false
  }
}
```

`FAILED` 会让 WES 进入阻断、对账或人工处理流程。

## 8. Trace 与诊断

联调时不要只看 HTTP 200。用 Trace 核对 Session、Command、Inbox、Outbox、Timeline 是否按顺序推进。

### 8.1 查询完整 Trace

```bash
curl -sS "$WES_API/workline/trace/trace/$TRACE_ID" \
  -H "Authorization: Bearer $WES_TOKEN" | jq
```

### 8.2 按 `command_code` 查询 Trace

```bash
curl -sS "$WES_API/workline/trace/command/$COMMAND_CODE" \
  -H "Authorization: Bearer $WES_TOKEN" | jq
```

### 8.3 查询阻塞点

```bash
curl -sS "$WES_API/workline/trace/$TRACE_ID/blocking-point" \
  -H "Authorization: Bearer $WES_TOKEN" | jq
```

### 8.4 查询设备路径视图

```bash
curl -sS "$WES_API/workline/runtime/traces/$TRACE_ID/path" \
  -H "Authorization: Bearer $WES_TOKEN" | jq
```

### 8.5 Trace 验收点

正常流程应能看到：

- `callback_logs` 中有 `event` 和后续 `result`。
- `inboxes` 已处理完成。
- `commands` 按顺序生成并完成。
- `outboxes` 已派发完成。
- `sessions` 最终为 `COMPLETED`。
- 没有未处理的 blocking diagnostic。

## 9. 常见问题排查

| 现象 | 优先检查 | 处理建议 |
| --- | --- | --- |
| HTTP 401/403 | `X-App-ID`、`X-Timestamp`、`X-Signature`、权限 | 确认签名 path 是否正确；签名不包含 body |
| HTTP 422 | JSON 字段类型、必填字段、`data` 层级 | 业务字段必须放在 `data` 中 |
| START 返回 409 | WorkLine 是否 `STOPPED`、设备状态接口是否 `AUTO` / `IDLE`、`current_command_id` 是否为空 | 按响应 `reason_code` 处理；先让设备回空闲，再重发 `WORKLINE_START_REQUESTED` |
| 扫码 Event 返回 409 | WorkLine 是否仍为 `STOPPED` / `RECONCILING` / `ESTOPPED` | 先完成 START 准入；RECONCILING/ESTOPPED 需人工处理后再 START |
| Event 接收但没有命令 | 设备是否绑定 WorkLine，WorkLine 是否 active，`plugin_key` 是否 `rough_sorter` | 查询 Trace blocking-point 和工作线配置状态 |
| Result 被拒绝 | `command_code` 是否存在，`device_code` 是否匹配命令目标设备 | 不要复用旧 `command_code` |
| 业务 NG 被当成失败 | `result` 是否误传 `FAILED` | 测量 NG 应传 `SUCCESS`，并在 `data` 中给 NG 字段 |
| 命令不下发到设备 | 设备基础数据的 `host`、`port`、`protocol`、`callback_path` 是否正确，WorkLine 是否不是 `SIMULATION` | WES 只按设备基础数据拼 URL；`SIMULATION` 是 WES 内部调试模式，不会调用设备地址 |
| 命令派发前被拒绝 | 设备状态接口是否非 `AUTO` / `IDLE`，或 WES 设备主数据是否 `RUNNING` / `ERROR` / `OFFLINE` | 先复位设备状态；确认 status 响应和 WES 设备状态一致 |
| 设备拒收 WES 命令 | 设备侧命令接口是否要求额外认证 | 当前 WES 命令下发不带设备回调签名 Header；如需认证需提前约定 |
| 设备收到重复命令 | ACK 是否超时、WES 是否重试 | 设备必须按 `command_code` 做幂等 |
| Q19 未通过或 provider 失败 | Trace 中 Q19 typed decision 或稳定 provider failure evidence | `REJECT` 按 WES 后续 NG 语义执行；provider failure 当前 fail-closed，T6 未闭环 Session Hold，设备侧不要补造命令或 Result |
| `MOVE_FORWARD` 后不生成 `PUT_TO_BIN` | `bin_allocator`、active bin rack、料箱/料格资源是否可用 | 查询 blocking-point；先补齐 WES 资源域配置 |

## 10. 联调验收标准

下面项目都通过后，粗分机基础交互联调通过。

### 10.1 基础协议验收

- 设备成功上报 `SCAN_COMPLETED`，WES 返回 HTTP 200。
- 现场 START 能通过准入，WorkLine 从 `STOPPED` 进入 `READY`。
- 设备状态接口能返回所有命令目标设备的 `AUTO` / `IDLE` / `current_command_id=null`。
- WES 能按 `trace_id` 查到 callback log 和 `DEVICE_EVENT` inbox。
- 设备能接收 WES 下发的 `PICK_AND_PUT`、`MOVE_FORWARD`、`PUT_TO_BIN` 或 `MOVE_TO_NG`。
- 设备用 HTTP 200 完成 ACK。
- 设备按 `command_code` 回传 `SUCCESS` result，WES 能推进下一步命令。
- 测量业务 NG 使用 `SUCCESS + data.NG` 表达，WES 进入 `MOVE_TO_NG`。
- 设备动作失败使用 `FAILED + error_detail` 表达，WES Trace 中能看到故障码和人工处理建议。

### 10.2 业务流程验收

- 出料资源配置满足时，正常主流程最终 Session 状态为 `COMPLETED`。
- Trace 中无未处理 pending outbox。
- `MOVE_FORWARD` 后如果资源域未满足，Trace 能清晰显示 blocking-point，双方能确认该阻塞不是设备协议问题。
- 急停、对账或人工处理解除后，WorkLine 回到 `STOPPED`，必须重新 START 后才能继续接收生产事件。

## 11. 供应商交付清单

硬件方在本系统管理界面维护：

- 设备命令接收 HTTP 服务地址、端口、`callback_path`、`status_path`、协议 `http` / `https`。

硬件方同步给 WES 项目组确认：

- 每台设备的 `device_code`、角色、能力清单和最大并发。
- 设备命令接收接口的认证方式；如果不是纯内网或白名单 HTTP 200 ACK，需要提前提供认证方案。
- 设备状态接口响应样例，至少覆盖 `AUTO` / `IDLE`、忙碌、手动模式、异常状态。
- 命令 ACK 响应样例和设备内部 `trace_id` 规则。
- 每类 `task_type` 的成功 result 样例、失败 result 样例和业务 NG 样例。
- 设备错误码字典。
- 现场网络连通性说明：WES 到设备、设备到 WES 的防火墙和白名单。
- 幂等策略说明：同一 `command_code` 重复下发或同一 `event_id` / result 重复回调时设备侧处理方式。

## 12. 关键原则

- 业务字段只放在 `data` 或 `params` 中。
- `command_code` 由 WES 生成，设备不得自造或覆盖。
- `command_code` 是设备 Result 的唯一强锚点。
- 业务 NG 不等于设备失败。
- 设备失败才使用 `result=FAILED`。
- 设备必须按 `command_code` 实现幂等。
- `STOPPED` / `RECONCILING` / `ESTOPPED` 不接收生产事件，必须先通过 START 或人工恢复流程。
- WES 派发设备命令前会检查实时状态，设备必须准确返回 `mode`、`status`、`current_command_id`。
- WES 只按设备基础数据的 URL 下发命令；目标是 Mock 还是真实设备由 `host:port` 配置决定。
- 现场排障优先使用 Trace 和 blocking-point 接口。

## 13. 附录：最小设备服务示例

可以先用下面的伪代码确认 WES 能否把命令打到设备侧服务。真实设备程序按供应商自己的框架实现，但行为保持一致：收到命令立即返回 HTTP 200 ACK，动作完成后再异步调用 WES Result。

```text
POST /api/v1/device/command
  1. 读取 JSON：device_code、command_code、task_type、params。
  2. 按 command_code 做幂等检查。
  3. 记录设备本地日志。
  4. 立即返回 HTTP 200。
  5. 设备动作完成后，调用 WES /api/v1/callback/result。
```

最小 ACK 响应：

```json
{
  "code": 200,
  "message": "OK"
}
```
